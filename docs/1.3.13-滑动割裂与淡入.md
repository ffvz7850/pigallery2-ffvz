# 1.3.13 — 滑动割裂的定位与淡入修复

## 用户体感

1. 滑动有点不顺滑。
2. 有些大图估计是"窗口没解码进去"，一滑动就瞬间上屏；真不行就加个淡入，别那么割裂。
3. 底图换个色，白黄一点。

---

## 一、先量：不顺滑到底卡在哪

写 `pg2-test/big_probe.js`，拿**全是大图**的目录（`未压缩4/蠢沫沫 宴`，35 张、单张 57~64 MB）逐屏测：
进入视口那一刻原图是否已就绪、多久上屏、这段有没有长任务。

改版前（1.3.11）：

```
{"readyAtEnter":false,"bgReady":true,"tToShow":3364,"sizeMB":62.9}   ← 首屏
{"readyAtEnter":true,"tToShow":0} × 9
SUMMARY {"notReadyAtEnter":1,"slowToShow":1,"maxShow":3364,
         "longTasks":4,"longMax":1762,"decodeMs":[2384,1235,1233,1232,1232,1231]}
```

两件事被钉死：

- **`decodeMs` 1231~2384 ms** —— 一张 8736 px 的 JPEG，Chromium 解码一次就要 1 秒以上。
  这不是 JS 的锅，是像素量的锅（8736×11648 ≈ 1 亿像素，而屏幕只要 1280×900）。
- **`longMax 1762 ms`** —— 首屏那张解码时主线程被占了 1.7 秒。用户点开竖图，看着 720 糊图
  等 3.4 秒，中途页面几乎没反应。

而滚动阶段的 9 屏全是 `readyAtEnter: true / tToShow: 0` —— **预载是有效的**，
只要用户滚得比 1.2 秒/张慢，滚过去就是已经解码好的图。

所以"不顺滑"是**两个独立问题**叠在一起：
① 单张超大图解码本身就贵，后台解码也会吃掉 CPU；
② 上屏那一下没有过渡，图是"啪"地整屏出现。

---

## 二、为什么"啪"一下：transition 的隐形前提

原来写的是：

```css
.vf-item img { opacity: 0; transition: opacity 0.16s; }
.vf-item img.vf-ok { opacity: 1; }
```

看着没毛病，但**transition 有个硬前提：起始值必须已经被渲染过**。
虚拟滚动的实际时序是：

```
同一帧内：  img 挂载（opacity: 0） + load 事件同步触发 + 加 vf-ok（opacity: 1）
```

浏览器在这一帧只知道"要画 opacity 1"，那个 0 从来没被 paint 过 → **过渡不启动，直接以 1 绘制**。
所以问题不是"淡入太短"，是**淡入压根没跑**。

用 `MutationObserver` + `transitionend` 实测确认（1.3.12）：

```
t=5ms   attach  0319.jpg  cls=vf-full        op=0
t=10ms  load    0319.jpg  cls=vf-full        op=0
t=51ms  class   0319.jpg  cls=vf-full vf-ok  op=0    ← 加 class 时仍是 0
t=229ms transitionend                        op=1    ← 178ms 渐变
```

---

## 三、修法两次迭代

### 第一版：双 requestAnimationFrame（能用，但太贵）

在 JS 里等两帧再置 `loaded`，保证 0 那帧真的被画过：

```ts
requestAnimationFrame(() => requestAnimationFrame(paint));
```

淡入确实来了（178 ms 渐变），但代价立刻在指标上显形：

| | scriptMs | styleCount |
|---|---|---|
| 1.3.11（无淡入） | 560 / 561 | 17 |
| 1.3.12（双 rAF） | **827** | **51** |

原因：**zone.js 把 `requestAnimationFrame` 也 patch 了**，每个 rAF 回调结束都会触发一次
全应用变更检测。滚 40 次 × 每屏 1~2 张 × 2 个 rAF ≈ 上百次额外 tick。

### 第二版：改用 CSS animation（采用）

`transition` 需要"起始值渲染过"，**`animation` 不需要** —— 它带 `from` 关键帧，class 一加上就从 0 播到 1，
而且 opacity 动画跑在合成线程，主线程一分钱不花：

```css
.vf-item img.vf-ok { opacity: 1; animation: vf-fade-in 0.18s ease-out; }
@keyframes vf-fade-in { from { opacity: 0 } to { opacity: 1 } }
```

JS 回到最朴素的 `item.loaded = true; detectChanges();`，双 rAF 全删。

逐帧采样验证（`fade_probe3.js`，滚动那一刻开始每帧读 computed opacity）：

```
ROUND0  0319.jpg: [0, 0, 0.23, 0.34, 0.44, 0.53, 0.62, 0.7, 0.78, 0.84, 0.9, 0.95]
ROUND1  0320.jpg: [0, 0, 0, 0.12, 0.23, 0.34, 0.44, 0.53, 0.62, 0.7, 0.78, 0.84]
        animationDuration: 0.18s
```

### 甩动时不再"直接置终态"

原来 `.vf-instant` 是 `transition: none` —— 甩动中上屏的图完全没有过渡，停下来那一下最容易看到"啪"。
改成压短而不是取消：

```css
.vf-root.vf-instant .vf-item img.vf-ok { animation-duration: 0.08s; }
```

实测：甩动中 `instant: true / 0.08s`，停手后 `instant: false / 0.18s`。

## 四、底图换成暖米褐

上一版是中性灰 `#2b2b2b`（17%），偏冷。这一版改成 `#4e4636`（rgb 78,70,54，约 28%，r>g>b）。
暖调跟人像/室内照片接得上，缩略图和原图淡入进来像"从暖暗处显影"，不是从冷灰里蹦出来。

候选梯度（`pg2-test/shots/swatch.png`）：

| 色值 | 感觉 | 亮度 |
|---|---|---|
| `#2b2b2b` | 中性灰（旧） | 17% |
| `#3a352c` | 暖褐灰 | 21% |
| `#48402f` | 更亮 + 更黄 | 26% |
| **`#4e4636`** | **暖米褐（当前）** | **28%** |
| `#5a5140` | 米褐 | 32% |
| `#6d6350` | 浅米黄 | 39% |

只改 `--vf-void` 一个数就能换档。

## 六、还没解决的：800 ms 的解码本身

`#4e4636` 和淡入解决的是**观感**。真正贵的那一步还在：

> 屏幕只有 1280×900，却要解码一张 8736×11648（约 1 亿像素）的图，`decode()` 稳定 800~1200 ms。

只要用户滚得比这快，就一定会撞上"等图"。唯一的根治办法是**别让浏览器解码那么大的图** ——
让服务端给 1440 档：

- 体积约 1/40，解码约 30~60 ms（快 15~20 倍），`decodeMs` 那一列会直接从 800 掉到几十毫秒；
- 代价：① 服务端**首次**访问要现生成（约 450 ms/张，之后进临时目录缓存）；
  ② 2560 宽的屏幕上 1440 会略软（约 1.8 倍放大）。

技术上要做三件事：

1. `config.json` 里 `Media.Photo.thumbnailSizes` 从 `[720]` 改成 `[720, 1440]`
   （`Localizations` 式的目录扫描不涉及这里，但**必须先确认 pg2 不会因此触发全库重建**）；
2. flow 组件对"超大图"（`metadata.size.width > 3000`）改走 `getBestSizedMediaPath(1440, 2400)`，
   普通图继续用原图，画质不受影响；
3. 可选：后台先把这个 1440 档批量生成一遍，避免首次浏览卡顿。

这一项要动你的 `config.json`，所以我没擅自做 —— 你说一句我就上。
