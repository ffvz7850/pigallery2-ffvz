## 一、最终改了什么

### 1. 撤销 1440 降档（用户明确要求）

| 位置 | 改动 |
|---|---|
| 常量 | 删 `LARGE_PIXELS = 20000000` |
| `srcOf()` | 恢复无条件 `getOriginalMediaPath()`，删掉按像素数选 `getBestSizedMediaPath()` 的分支 |
| `onResize()` | 不再清 `originalPath`（原图 URL 与视口无关） |
| `config.json` | `Media.Photo.thumbnailSizes` 从 `[720, 1440]` 恢复 `[720]`（脚本 `9r_config_restore_720.sh`） |

顺带把 `srcOf()` 注释里那句「会把 720p 挤出解码缓存」删掉了——上一轮那句因果链不严谨：已上屏的 `.vf-bg` 不会被资源淘汰带走，真正受影响的是**整层的栅格化**，见下一条。

### 2. 加载链路收拢（本轮核心）

原 1.3.6 的预载链路有两套状态：`startDownload()` 离屏 Image 下载 → `enqueueDecode()` 按距离插队 → `pumpDecode()` 用 `MAX_DECODES=2` 分槽 → `markReady()` 标 `decoded`，同时 `holdImg()` 保引用；DOM 侧 `reveal()` 又按 `item.decoded` 决定要不要再 `decode()`。**下载、解码、就绪、DOM 上屏各管一摊，共 6 个方法 + 4 个集合字段。**

现在收拢为：

```
startDownload()  →  onload:
                     ├─ inFlight.delete + pump()        下载槽立刻接下一张
                     ├─ markDownloaded()  → fetched=true + holdImg()   文件到手、保住引用
                     └─ img.decode()                    后台解码，不排队、不占槽、不在关键路径

DOM [src] 挂载即发（与预载 in-flight 合并）→ onImageLoad → reveal()
                     └─ item.fetched ? 直接淡入 : 现场 decode() 一次
```

删掉的：`decodeQueue`、`decoding`、`MAX_DECODES`、`enqueueDecode()`、`pumpDecode()`、`markReady()`、`KEEP_DECODED`、`item.decoded`。
新增的：`fetched` 语义、`markDownloaded()`，净减少约 55 行。

视频封面同样统一：`posterDecoded` 只由 DOM 的 `onPosterLoad` 设置，不再由预载路径抢先置位。

### 3. 打底图独立合成层

`.vf-item` 带 `will-change: transform`，`.vf-bg` 与 `.vf-full` 原本共用同一合成层，大图解码冲击栅格缓存时会一起被丢。现在给 `.vf-bg` 加 `transform: translateZ(0) + will-change + backface-visibility`，提升为独立层；它常驻不撤、opacity 恒 1，原图只负责在上面淡入。

### 4. 主色兜底（首次部署）

1×1 canvas 取平均色存 `item.dominant`（3 字节/张），绑定到 `.vf-item` 的 `background-color`。这是唯一不依赖请求、不受任何缓存淘汰影响的兜底：缓存被清、缩略图 404、新图还没生成，最坏退到色块而不是纯黑。配合 `.vf-bg` 的 `#141414` 兜底色。

### 5. 首次部署的另两项（源码上一轮已改、本轮才上线）

- 甩动时打底窗口从 2 张临时扩到 12 张（`FAST_THUMB_AHEAD`），停下恢复；
- 缩略图通道并发 4 → 6（`MAX_THUMB_DOWNLOADS`）。

## 二、两次返工：都是实测把推断打回来的

这一版中间构建过三次，前两次都被 A/B 数据否掉，过程值得留档。

### 返工 1：让 DOM 延迟拿 src → 反而多下了 5 MB

第一版想彻底消除「两个下载者」，把模板改成 `[attr.src]="fullSrcOf(item)"`，只有预载完成后才放行 `src`。

实测（`v137_test.js`，344 张目录）：

```
1.3.6   REQUESTS dist {"1":21}                     ← 每个 URL 只有一条请求记录
第一版  REQUESTS dist {"1":13, "2":8}, pairs[0]:
        0319.jpg  s=8325  tr=5,097,816
        0319.jpg  s=10121 tr=5,097,816           ← 1.8 秒后又完整传了一遍
```

原图响应头是 `Cache-Control: public, max-age=31536` + ETag，但 Chromium 没复用这次相隔 1.8 秒的请求。1.3.6 之所以只有一条，是 DOM 挂载即发、与预载的 in-flight 请求时间重叠被合并，且 `holdImg()` 持有引用保住了缓存资源。

**回退**：删除 `fullSrc / posterSrc / ensureSrc / fullSrcOf / posterSrcOf`，模板恢复挂载即发 `[src]`；保留 `holdImg()`。第二版实测 `dist {"1":21}`、`pairs: []`。

> 教训：想靠「延后放行」省掉第二个下载者，在这个环境里等于把 in-flight 合并拆成两次独立请求。原图是 5 MB 级，这个代价比重复解码大得多。

### 返工 2：把 decode 全挪到 DOM → 上屏从 11 ms 退化到 1478 ms

第二版按「提前解码不可靠、应挪到挂载前一帧」的推断，删掉离屏 `decode()`，让 `reveal()` 每次都在 DOM 上现场解码。A/B（同脚本、同容器挂载、同 600 ms 延迟）：

| 版本 | 即时上屏 | p50 |
|---|---|---|
| 1.3.6 | 12/14 | **11 ms** |
| 第二版 1.3.7 | 6/14 | **1478 ms** |

**上一轮那条架构推断在这台环境不成立**：Chromium 确实复用了离屏预解码的位图，DOM 挂载几乎零成本；把 `decode()` 放进上屏关键路径反而要等解码队列。

**修正**：恢复离屏后台 `img.decode()`（就写在 `onload` 里一行，不重建解码队列/分槽状态机），`reveal()` 对 `item.fetched` 的项直接淡入。最终版 12/14、p50 12 ms，且离屏解码次数从 1.3.6 的 16 次降到 8 次。

> 教训：「简化」要砍的是调度状态机，不是已被实测证明有效的预解码本身。

## 五、已知限制

1. 镜像 1.15 GB：从 `1.3.6` 派生，`rm -rf dist` + `COPY` 多留一层。需要瘦身时从 1.3.2 一次成型可回到 1.08 GB。
2. 极端压力（深处 + 100 ms 人工延迟 + 连甩 40 次）下仍有 28% 挂载未就绪；靠主色兜底把可见槽位覆盖到 92.6%，但那部分仍是色块而非图，不是 100% 无降级。
3. 新加入、尚未生成缩略图的图首次仍需约 450 ms 冷生成；用户库已全量预生成，未覆盖此路径。
4. `fetchPriority='high'` 对离屏 `new Image()` 在 CDP `initialPriority` 里仍报 Low（Chromium 行为），打底不依赖该提示，靠 40 KB vs 5 MB 的体积差。
5. 1440 档已按要求撤销；若将来要处理超大图，需要重新评估「降档」与「独立合成层」的取舍。
