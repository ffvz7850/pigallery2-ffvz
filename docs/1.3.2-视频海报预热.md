# 1.3.2 — 视频海报预热（竖图流里视频不再先黑一块）

> 基线：`ffvz/pigallery2:1.3.1`（= 1.3.0 的 https/h2 + 预载即解码）。
> 本次只改 `flow/` 组件三件套 + 一处 Dockerfile 卫生问题，upstream 文件零改动。
> 测试容器 `pigallery2flow`：`8285`(http) / `8286`(https)，现网 8282 未动。

---

## 一、问题

竖图流往下滑，滚到**视频**时：先出现一块纯黑（占位框），过一拍才“啪”地跳出封面。

照片这条路径在 1.3.1 已经解决了（预载即解码 + 缩略图预热），**视频从来没走这条路** —— 1.3.1 的审查表里它被标成「第 7 项：低，已知未改」。

## 二、根因（三处都绕过了视频）

| # | 位置 | 原实现 | 后果 |
|---|---|---|---|
| 1 | `pump()` | `if (!item \|\| !item.gridMedia.isPhoto()) continue;` | 视频项直接跳过，**海报从不预载、从不解码** |
| 2 | `warmThumb()` | `if (item.thumbWarmed \|\| !item.gridMedia.isPhoto()) return;` | 视频没有占位底图 → 底下是 `#0b0b0b` 纯黑 |
| 3 | `bgOf()` | `if (!item.gridMedia.isPhoto()) return null;` | 同上，`.vf-item` 的 `background-image` 为空 |

于是视频项挂载时：`<img class="vf-poster" [src]>` 插入 DOM **才开始**发请求 → 下载（几十 KB）→ 现场解码 → 出图。这段时间就是那块黑。

## 三、改了什么

### 1. 视频项也进预载队列（`pump()` 分流）

视频没有“原图可当图片预载”——`srcOf()` 指向的是 mp4 文件，塞进 `Image()` 会把整个视频下下来。所以按类型分流：

```ts
if (item.gridMedia.isVideo()) {
  this.prefetching.add(index);
  this.warmThumb(item);
  this.warmPoster(item, (): void => { this.prefetching.delete(index); this.pump(); });
  continue;
}
```

`prefetching` 仍占一个并发位（`PREFETCH_CONCURRENCY = 2`），避免一次冲出一堆海报请求。

### 2. 新增 `warmPoster()`：下载 + 解码，且按 URL 去重

```ts
private warmPoster(item: FlowItem, onDone?: () => void): void {
  if (onDone) {
    if (item.posterDecoded) { onDone(); return; }
    (item.posterCbs = item.posterCbs || []).push(onDone);
  }
  if (item.posterWarmed) return;      // 同一张只有一次请求
  item.posterWarmed = true;
  const url = this.posterOf(item);
  const settle = (): void => {
    item.posterDecoded = true;
    const cbs = item.posterCbs || []; item.posterCbs = undefined;
    cbs.forEach((cb) => cb());
  };
  const im = new Image();
  im.fetchPriority = 'low';
  im.onload = () => im.decode ? im.decode().then(settle).catch(settle) : settle();
  im.onerror = () => settle();        // 抽帧失败不重试，别堵队列
  im.src = url;
}
```

两个调用点：
- `pump()` 里（预载队列，带 `onDone` 归还并发位）
- `updateWindow()` 里对**马上要挂载**的视频项各调一次（不带回调，只提前发请求）

回调挂在 `item.posterCbs` 上而不是组件级数组：窗口预热和队列预热可能同时命中同一张，必须共享同一次请求，否则并发位会永久漏掉、队列卡死。

### 3. 视频项补上占位底图

`bgOf()` 去掉 `isPhoto()` 判断，`warmThumb()` 同理。视频的 `getThumbnailPath()` 同样是服务端生成的 jpg 缩略图，网格里本来就是它 —— 同一 URL，缓存命中，零额外请求。

现在视频项的层次和照片一致：**缩略图（糊）→ 海报（清）**，中间不会露黑。

### 4. 模板 + 样式

```html
<img class="vf-poster" [class.vf-ok]="w.item.posterDecoded"
     [src]="posterOf(w.item)" alt=""
     (load)="onPosterLoad(w.item, $event)"
     (error)="onPosterError(w.item)"/>
```

```css
.vf-poster { opacity: 0; transition: opacity 0.16s ease-out; }
.vf-item img.vf-poster.vf-ok { opacity: 1; }   /* 特异性要压过 .vf-item img 的 opacity:0 */
```

注意：不能只写 `.vf-ok`。`.vf-item img.vf-poster` 和 `.vf-item img.vf-ok` 特异性相同，前者写在后面会赢，海报会一直是透明。

## 四、顺手带掉的三个 bug

| # | 问题 | 修法 |
|---|---|---|
| 1 | `posterOf()` 的 URL 带窗口尺寸档位（`/720`、`/1080`），但 `posterPath` 缓存到 item 上，**resize 后一直用旧尺寸** | `onResize()` 里清空全部 `posterPath / posterWarmed / posterDecoded / posterCbs`，让 `updateWindow(true)` 重算 |
| 2 | 视频项从来没做过比例纠正（只有照片的 `onImageLoad` 会）→ metadata 缺尺寸或不准时，横屏视频被塞进 3:4 的框，上下大片黑边 | `onPosterLoad()` 拿 `naturalWidth/Height` 走同一套 `pendingRatios` 合并 flush |
| 3 | `onPosterError()` 若沿用 `item.failed = true`，海报会变成 0.35 透明度（照片的“失败态”语义） | 视频封面失败只置 `posterDecoded = true` 放行，底下有缩略图占位，播放按钮照常可用 |

## 五、验证

浏览器：Playwright + Edge，1280×900，`https://192.168.0.10:8286`（h2），真实图库目录（28 项 / 3 个视频）。

用 `PerformanceObserver` 抓 resource 时间轴 + `MutationObserver` 抓 `.vf-poster` 插入 DOM 的时刻，逐个比对**请求发起/下载完成**与**元素挂载**的先后：

```
mounts = 11
pre    = 11     ← 挂载前请求就已发起
post   = 0      ← 挂载后才发请求的数量（原来就是全部）
downloaded = 11 ← 挂载前下载已完成
decodedBefore = 11
leadEnd = 2343~2345 ms（首次进入）   / 16091 ms（滚回来那一次）
海报大小 = 23 / 41 / 57 KB（720 档）
```

- 11/11 全部命中“挂载前已下载完”，**没有任何一次是挂载现场才开始下**
- 滚走再滚回：`leadEnd` 16 秒，说明依旧是那次预载的请求，没有重复拉取
- 视频项 `background-image` 非空（`bg: true`），海报 `opacity: 1`、`naturalWidth: 720`
- 截图暗像素占比（`<12` 灰度）：`v-00 0.0% / v-01 0.0% / v-05 0.0% / v-back 0.0%`（个别帧 3~4% 是素材本身暗部）
- `v-00` 与 `v-back` 的平均灰度完全一致（159.2）→ 滚回原位画面无残留闪烁
- 控制台零报错

## 六、镜像卫生（顺手修的）

`COPY dist /app/dist` 是**合并**，不会清空基础镜像里的目录，所以每版都会留下一份上一代的 `*main.<hash>.js`：

```
/app/dist/zh/zh.main.4a6cbc990c409973.js   ← 1.3.0 残留
/app/dist/zh/zh.main.7a0dda63828ad975.js   ← 当前
/app/dist/zh/zh.main.d22fc87647edda1.js    ← 1.3.1 残留
```

这次实测确认我们的 `dist` 是 1.1.6 的**完整超集**（`comm -23` 差集为 0 个文件），所以 Dockerfile 改成先删再拷：

```dockerfile
RUN rm -rf /app/dist
COPY dist /app/dist
```

结果：`zh/` 下只剩一个 `zh.main.7a0dda63828ad975.js`。以后按 bundle 名审计版本不会再被旧包骗到。
