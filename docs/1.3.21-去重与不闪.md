## 一、三件事的根因

### 1) 同一张 720 被挂了两份

`.vf-bg` 和 `.vf-full` 在非当前张上指向**同一个 URL**：

```ts
thumbOf(w) → getBestSizedMediaPath(720,720)   // .vf-bg
srcOf(w)   → 非当前张 → lowUrlOf(w)            // .vf-full —— 同一个 720
```

网络层浏览器会去重（只发一次），但 DOM 里是两张 `<img>` 拉同一张图：多一份解码位图、
多一层合成。视频更绕：`.vf-poster` 用的 `getBestSizedMediaPath(innerWidth, innerHeight)`
在「缩略图只有一档 720」的配置下也是同一个 720，等于三份。

> 顺带确认：网格缩略图走的 `getThumbnailPath()` 最终也落到 `/720`，**Url 完全相同**，
> 服务端对 720 是 `max-age=1 年`。所以「网格和竖图流各拉一遍」这件事本来就不存在 ——
> 实测打开灯箱后 720 的唯一 URL 124 个、回源次数也是 124，零重复。

### 2) 关掉 720 底图后滑动会闪

```ts
// 1.3.20（错）
return settled || isCurrent ? this.hdUrlOf(w.item) : null;  // ← 甩动中非当前张返回 null
```

甩动判定一触发（`fastRate` 1.2px/ms，随手一滑就超），**整屏除当前张以外的 `<img>` 全被
`*ngIf` 摘掉** → 有图变底色 → 停手 200ms 后全部重新挂回来 → 重新解码 + 淡入动画重播。
一次滑动能看到两次「全屏闪」。

### 3) 2160 也会被滑动弄闪

当前张换到下一位时，上一张的 `src` 从 `/2160` 被改回 `/720`（「只给当前张高清」的规则）。
同一个 `<img>` 换源 = 重新解码，画质还会当场掉一档再回来。

## 二、改法：URL 变成「粘性」

`FlowItem` 新增 `fullSrc`，语义是「已经绑到这个 `<img>` 上的 URL」，**一旦写入就永不回退、永不置空**：

```ts
public fullSrcOf(w: FlowWindowItem): string {
  const it = w.item;
  if (!it.gridMedia.isPhoto()) { return null; }
  if (it.fullSrc) { return it.fullSrc; }        // ← 粘住：滑动/甩动都不动它
  const settled = !this.fastScrolling;
  const isCurrent = w.index === this.current;
  if (this.tuning.lowEnabled) {
    return settled && isCurrent ? (it.fullSrc = this.hdUrlOf(it)) : null;   // 非当前张只留底图那一份
  }
  return settled || isCurrent ? (it.fullSrc = this.hdUrlOf(it)) : null;
}
```

三件事一次解决：

- **不摘元素**：`*ngIf` 只在「还没轮到绑」时为 false，绑过之后永远是字符串 → 元素常驻
- **不换源**：滑走不是当前张了，URL 不变 → 那个 2160 继续显示，不降级重解码
- **不重复挂**：有底图时非当前张**根本不挂 `.vf-full`**，720 只由 `.vf-bg` 出一次

底图那边反过来：**不按「大图已上屏」撤掉**。撤掉的瞬间大图正在淡入（opacity 从 0 起），
底下那层一没就先露一帧底色 —— 那正是要治的闪。所以 `.vf-bg` 在有底图时全程常驻，
它只是垫在下面，成本是每项一份 720 位图。

其他配套：

- 视频：`needBg()` 比较 `posterOf === thumbOf`，相同就**不挂底图**（只有一档缩略图时必然相同）
- `onImageError`：2160 生成失败过就置 `previewFailed` 并换回 720（粘性 URL 的副作用是
  「失败也会被粘住」，必须显式换一次源，否则那张永远空着）
- `applyTuning()`：压缩档位**或底图开关**变了才整体重置 `fullSrc`（只看档位的话，
  拨开关后老 URL 会一直粘着）
- 诊断条新增「已绑 x」，并把「预热 2 张」改成关底图时显示「跳过（无底图，窗口自取）」

## 三、实测

### 结构（`v1321_test` 14/14，测试容器 8286 与现网 8284 双绿）

```
开底图：打开时只有当前张挂 vf-full      nFull=1 nItem=3 nBg=3
开底图：没有「一张图两份 img」          dup=0
开底图：滑动中已上屏的元素不被摘        rm=0 add=0
开底图：滑动中已绑定 src 不被改         srcChange=0
开底图：滑走的那张仍保留自己的 2160     hd=1 low=0
关底图：甩动中已上屏的 vf-full 不被移除 rm=0
关底图：甩动中已绑定 src 一次都不改     srcChange=0
关底图：停手后新窗口每张都上屏          nFull=4/nItem=4 等待=1023ms
复看已看过的图：2160 不再回源           新增回源=0
```

`rm` / `srcChange` 用 `MutationObserver` 抓 `.vf-canvas` 下的元素增删与 `src` 属性变更
（只算「把非空 src 改掉」，新元素首次赋值不算）。

### 网络

| | 唯一 URL | 回源次数 |
|---|---|---|
| 720 | 124 | 124（零重复） |
| 2160 | 2 | 2 |

打开灯箱是在网格已经拉完 124 张缩略图之后，**竖图流没有额外回源一次 720**。

### CPU（滑动 1s，冷/热各一次）

| | peak | avg |
|---|---|---|
| 冷缓存（真生成 2 张 2160） | 203% | 25% |
| 热缓存 | **21%** | **2%** |

冷缓存的 203% 是两次 2160 生成撞在一起（当前张 + 预热），和 1.3.19 同量级；
热缓存从 1.3.19 的 98%/5% 降到 21%/2%。

**两条旧断言改了口径**（不是回归，是行为有意改变）：
- `v1317_test` 的「甩动中不请求 2160」原来查 `src` 里不许出现 2160；现在已上屏的 2160 会粘住，
  改成查「甩动前后 2160 的 Resource Timing 条目数不变」—— 真正要防的是新起请求。
- `v1320_test` / `v1317_test` 的「全部已上屏」原来数 `.vf-full.vf-ok`；现在非当前张只有底图，
  改成「大图已上屏 **或** 底图已就绪」。
