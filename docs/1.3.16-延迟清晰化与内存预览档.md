## 一、甩动中先不上屏（延迟清晰化）

### 改了什么

`reveal()` 的放行时机从「解码完成」改成「解码完成 **且** 不在甩动」。

```ts
private reveal(item: FlowItem, img: HTMLImageElement): void {
  const show = (): void => {
    if (item.loaded) return;
    if (this.fastScrolling) {        // ← 新增：只标记，不上屏
      item.ready = true;
      this.pendingReveal.add(item);
      return;
    }
    item.loaded = true;
    this.cd.detectChanges();
  };
  img.decode().then(show).catch(show);
}
```

停手时（`setFastScrolling(false)` → `flushPendingReveal()`）一次放行。

### 为什么这样有效

原来「解码什么时候完成，图就什么时候出现在眼前」。滑得快时，一屏糊图刚怼到眼前、解码也刚好结束 —— 整张图就「啪」地变清晰。这个突变点和用户的动作毫无关系，人眼就读成「瞬间加载」。

现在突变点被钉死在**你停下来之后**：甩动全程画面只有 720 底图在动（连续、不突变），停手才统一显影。

甩动中 `src` 一直挂着、解码照常做，所以停手那一刻位图早就好了 —— 观感是「对焦」，不是「加载」。

配套：`fadeMs` 180→280、`fastFadeMs` 80→140、`fastSettleMs` 260→200。

### 实测（大图目录 未压缩4/蠢沫沫 宴）

```
甩动 10 屏，逐帧统计「新出现的已上屏项」：[0,0,0,0,0,0,0,0,0]
（甩动前已在屏上的 3 张保持不动：all=[3,3,3,2,1,1,0,0,0]）
停手后放行：t=4093ms，且 inst=false（确认发生在甩动结束之后）
```

甩动中确实是 0 —— 没有任何一帧在甩动中途冒出清晰图。

## 二、2160 内存预览档（不落盘）

### 为什么不能走 `thumbnailSizes`

PiGallery2 的缩略图请求一律经 `PhotoProcessing.generateThumbnail` 写到 `tempFolder/tc` 并长期留着。竖图流的 2160 只服务「这一眼看清」，按库容量算会吃掉几十 GB。

### 怎么做

新增 `src/backend/middlewares/thumbnail/MemoryPreviewMWs.ts`：

- `sharp` 直接出 Buffer，`res.send(buf)`，**磁盘上不产生任何文件**
- 进程内 LRU：24 张 / 96MB，先到先淘汰
- 在 `ThumbnailGeneratorMWs.generateThumbnailFactory` 的 **size 校验之前**拦截，否则会被回落成 `thumbnailSizes[0]`（720）
- 新路由 `GET /pgapi/gallery/preview-cache`：清空内存并返回 `{items, bytes}`
- 关灯箱时前端调一次（`keepalive`，页面卸载也发得出去）

### 尺寸语义

按**短边**缩放（与 `PhotoWorker` 一致）：`Math.min(size, width/height)`，不放大。
2160 档 → 竖图 2160×2880，横图 2880×2160。输出 webp。

### 实测

| 指标 | 值 |
|---|---|
| 冷生成（1 亿像素 / 60MB 原图） | **2776 ms** |
| 热命中（内存 LRU） | **18~39 ms** |
| 产物 | webp 243KB，2160×2880 |
| 响应头 | `X-Pg2-Preview: memory` + `Content-Type: image/webp` |
| 落盘文件数 | **0** |
| tmp 目录大小 | 117M（与改前一致） |

## 三、一个必须说清的事实：冷生成比原图慢

顺手把成本分解了（`9at_bench.sh`，4 核 NAS）：

```
decode-only           2505ms   291MB raw        ← 1 亿像素全解码
decode+resize-2160    2026ms    18MB raw        ← 已用 JPEG DCT 缩小
webp e6 q80 2160      3557ms   268KB
webp e4 q80 2160      3035ms   288KB
webp e2 q80 2160      2577ms   301KB  ← 采用
jpeg q80 2160         3828ms   611KB
webp e2 q80 1440      8603ms   154KB  ← 反而慢 3 倍
webp e2 q80 1080      9153ms   101KB  ← 更慢
```

**两个结论：**

1. **2160 恰好是最便宜的档位。** `8736 ÷ 2160 ≈ 4.04`，命中 JPEG 的 DCT 1/4 缩小解码；1440 / 1080 不是整数分之一，退化成全量解码 + 高质量重采样，要 8~9 秒。所以「降档位换速度」在这里是反的。
2. **冷生成 2.7s 比原图（1s 下载 + 1s 解码）还慢一点。** 收益不在首次，在：
   - **内存**：位图 25MB vs 407MB，降 16 倍。这才是「大图把 720p 挤出解码缓存」的正解
   - **热命中**：再看同一张 18ms，原图要 800ms 解码

所以它换的是「内存 + 回看速度」，代价是「首次多 0.7s，且这 0.7s 有 720 底图兜着」。
不想要这个取舍，设置里把「压缩档短边」填 0 即可，立刻回到原图。

## 四、预热策略（两个坑都踩了）

`startPreGen` 打开时对当前张起的前 N 张发起低优先级 GET（不读 body，服务端生成完就够）。

第一版是**串行**、且**队列固定从打开位置开始**，实测两个问题：

1. 甩到第 10 屏后，它还在生成第 1~4 屏 —— 拿 CPU 生成你早已滑过的图，当前屏反而排不上队
2. 甩动中预热和当前图抢 CPU，停手后 3.3s 还没图

改成：

- **并发 2 路**（4 核上约 1.25s/张，正常浏览跟得上）
- **跟随锚点**：`updateWindow` 里发现 `|current - lastPreGenFrom| >= 2` 就重排队列
- **甩动时全部掐掉**（`preGenToken++`），停手再重启

改完：停手后 4093ms 放行（甩 10 屏的极端情况），常规滑动基本秒出。

`/admin` → 基础分组 →「界面缩放」旁边，新增两项（共 4 项）：

| 设置项 | 默认 | 说明 |
|---|---|---|
| 竖图流 · 压缩档短边 | **2160** | 0 = 关闭，永远原图。可选 1080 / 1440 / 2160（前端会自动对齐） |
| 竖图流 · 预热张数 | **4** | 打开时预生成前 N 张。0 = 不预热 |

灯箱内 `?vfdebug` 面板也能调，实时生效。诊断条新增一行：

```
压缩档 2160（内存，不落盘） · 待放行 0 · 底色 #4e4636 · 淡入 280ms
```

「待放行」> 0 表示有图解码完了、正在等甩动结束 —— 这就是延迟清晰化在工作。

## 八、切现网

现网 `pigallery2xin` 仍是 1.3.15。切换用「先 create 再换」，create 失败不动现网：

```bash

sudo docker create --name pigallery2xin_new \
  -e NODE_ENV=production -e TZ=Asia/Shanghai -e PUID=1000 -e PGID=1001 \
  -e PG2_TLS_HOST=192.168.0.10 -e Photo_photoLoadMethod=Original \
  -e default-Database-dbFolder=/app/data/db \
  -e default-Media-folder=/app/data/images \
  -e default-Media-tempFolder=/app/data/tmp \
  -e default-Extensions-folder=/app/data/config/extensions \

  -v "/vol2/1000/图库/photo":/app/data/images:ro \
  -v /vol1/1000/docker/pyxin/tmp:/app/data/tmp \
  -v /vol1/1000/docker/pyxin/config:/app/data/config \
  -v /vol1/1000/docker/pyxin/data:/app/data/db \
```

## 九、已知取舍 / 下一步

- 冷生成 2.7s 是解码的硬成本，除非接受更低画质或更强 CPU，没有别的办法
- 甩得很深（10 屏以上）时，停手仍要等 3~4s 才有清晰图（720 底图全程在）
- 如果实测觉得「首次慢」比「内存省」更痛，把「压缩档短边」设 0 即可回退，一行设置，不用回滚镜像
