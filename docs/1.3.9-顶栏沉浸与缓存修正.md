## 一、界面改动

### 1. 顶栏默认隐藏

- `hudVisible` 初值 `true → false`（字段 + `reset()` 两处）。
- 打开竖图时画面完全沉浸，没有任何 UI 覆盖；点一下画面才浮出计数与关闭键，再点收起。

### 2. 隐藏时关闭键也不能点（关键细节）

`.vf-topbar` 隐藏时是 `pointer-events: none`，但 `.vf-close` 自己写了 `pointer-events: auto` ——
CSS 里**子级的 auto 会把父级的 none 覆盖回来**。结果是「看不见的 × 仍然能点中」，
右上角随手一碰就把灯箱关了。补一条：

```css
.vf-topbar.vf-hidden .vf-close { pointer-events: none; }
```

### 3. 计数移到左上、与 × 同一条基线

`.vf-topbar` 从「flex 居中」改成「56px 高的定位容器」，两个子元素都锁在 0 ~ 56px 的带里：

| | 定位 | 垂直居中 | 实测 |
|---|---|---|---|
| 计数 `.vf-hud` | `left: 24px + safe-area` | `height:56px` + `flex align-items:center` | `hudCy = 32` |
| 关闭键 `.vf-close` | `right: 4px + safe-area` | `56×56` + `grid place-items:center` | `closeCy = 32` |

两者中心线完全相同（都 32px），所以是真正平齐，不是"看起来差不多"。

## 二、最有价值的一项：图片缓存头从 8.76 小时修成 1 年

`RenderingMWs.renderFile` 里原本是：

```ts
return res.sendFile(path, { maxAge: 31536000, dotfiles: 'allow' });
```

**express 的 `sendFile` 里 `maxAge` 单位是毫秒，不是秒。** 所以这个"一年"实际只有
`31536000 ms = 8.76 小时`，响应头是 `Cache-Control: public, max-age=31536`。

后果：昨天看过的文件夹，今天再打开要**整批重下**缩略图和原图 —— 滚动再快也要等网络。

改成字符串字面量，杜绝单位歧义：

```ts
return res.sendFile(path, { maxAge: '1y', dotfiles: 'allow' });
```

实测响应头（同一个 URL，1 年）：

```
原图  6.jpg     → public, max-age=31536000   len=1306960
缩略图 6.jpg/720 → public, max-age=31536000   len=39910
```

**这是本次唯一需要重启后端的改动**，收益是"回访同一目录零下载"。

> 副作用要知道：图片如果**同名原地替换**（不是新增），浏览器可能仍显示旧图，需要强制刷新（Ctrl+Shift+R）。
> 正常"加新图 / 改目录名"不受影响。

## 三、代码精简

| 删掉的东西 | 为什么是多余的 |
|---|---|
| `thumbPriority` 集合（字段 + 5 处读写 + 2 处排序键） | `refreshWanted()` 里两个循环把 `thumbWanted` 的每一项**同时**也加进 `thumbPriority`，两个集合恒等。所以 `pa = has(a)?0:1` 永远是 0，排序退化成纯距离；`im.fetchPriority` 三元也永远走 `'high'`。整个集合删掉，`fetchPriority = 'high'` 写死。 |
| `ItemCount` getter / `scrollToMedia()` | 全工程 grep 无引用（`lightbox.gallery.component` 只用 `CurrentIndex` / `isOpen` / `scrollToIndex`）。 |
| `onImageError` / `onPosterError` 里的 `cd.detectChanges()` | 这两个是模板 `(error)` 回调，Angular 自己会在本轮末尾检测 —— 对照 `onPosterLoad` 本来就没写，也一直正常。手动再检测一次纯属重复跑模板。 |
| `.vf-item { will-change: transform }` | 内联的 `translate3d(...)` 本身就会让每项提升为合成层，`will-change` 只是让层常驻显存、没有任何额外收益。 |
| `resize` 时对照片清 `fetched` / `thumbPath` | 见下。 |

### 顺手修掉的一个真实浪费

原来 `onResize` 对**整本目录**（几百项）执行：

```ts
it.posterPath = undefined; it.posterDecoded = false; it.fetched = false;
it.thumbPath = undefined; it.thumbWarmed = false;
```

但照片的原图 URL 与视口无关、打底图固定走 720 档也与视口无关 —— 清掉 `fetched`
等于让整本目录的原图**重新下一遍**。现在只对视频（封面 URL 带窗口尺寸档位）做重置。

## 四、调度上的小改

### 1. 甩动状态不再每帧新建 timer

原来 `setFastScrolling(true)` 每次滚动都 `clearTimeout` + `setTimeout` ——
甩动时每帧一次，等于每秒 60 个 timer 的创建/销毁。改成只记一个到期时间戳 `fastUntil`：

```ts
this.fastUntil = now + FAST_SETTLE_MS;
if (this.fastTimer === null) this.fastTimer = setTimeout(settle, FAST_SETTLE_MS);
```

`settle()` 醒来后看还剩多久，没到就把 timer 续到点为止。稳态下只有一个 timer。

### 2. 预载排序改成"方向优先"

原来 `Math.abs(a - cur) - Math.abs(b - cur)`：往回那张和往前那张一样近时会平白抢槽位。
新增 `sortByDirection()`，**行进方向上的（马上要看到的）一律排在回扫方向前面**，同向再比距离。
`pump()`（原图）和 `pumpThumb()`（打底图）共用同一个排序。

### 3. resize 防抖 + 按比例还原位置

- 防抖 `RESIZE_SETTLE_MS = 140`：拖窗口每秒几十次 resize，每次都 `rebuild()`（O(n) 遍历整本目录）
  会明显卡手。现在等尺寸稳定再做一次。
- **按比例还原偏移**：这一张的高度跟着宽度变了，原来按旧像素还原，画面会在同一张里往下滑一截
  （frac 0.68 → 0.87，等于"跳"了 19% 屏高）。改成 `off * newH / oldH` 后精确保持。

实测（1280×900 → 1000×760 → 1280×900）：

```
BEFORE frac=0.68   AFTER frac=0.68   BACK frac=0.68
```

### 4. 图片解码提示

模板上显式声明，避免浏览器把解码塞回渲染关键路径：

```html
<img class="vf-bg"   decoding="async" fetchpriority="high">
<img class="vf-full" decoding="async">
<img class="vf-poster" decoding="async" fetchpriority="high">
```

打底图和封面上 `fetchpriority="high"`：它们才是"不黑"的保障，原图（预载侧）已经是 `low`。

### 5. 每项做布局隔离

```css
.vf-item { contain: layout paint; }
```

滚动换项时只有变动的那一项要重算，不会把 canvas 上其余几项一起拖进重排。
（`overflow:hidden` 已经裁剪，`contain: paint` 不会改变可见结果。）

## 六、图加载参数：可调项一览（本次没动的）

生产走 HTTPS → **HTTP/2**（实测 `v=2`），所以不存在"每域名 6 连接"的上限，并发参数不用为它让路。

| 位置 | 现值 | 说明 |
|---|---|---|
| `MAX_DOWNLOADS` | 4 | 原图并发。内网千兆下一张 5 MB ≈ 0.1 s，4 条已足够 |
| `MAX_THUMB_DOWNLOADS` | 6 | 打底图并发。实测磁盘命中 83 张/秒，甩动只消耗 11 张/秒 |
| `AHEAD_DOWN / BEHIND_DOWN` | 6 / 2 | 向下滑预载多少张原图 |
| `AHEAD_UP / BEHIND_UP` | 3 / 5 | 向上滑时反过来 |
| `THUMB_AHEAD / FAST_THUMB_AHEAD` | 2 / 12 | 静止 2 张，甩动扩到 12 张 |
| `FAST_SCROLL_RATE` | 1.2 px/ms | 判甩动阈值，低于它才保留淡入 |
| `FAST_SETTLE_MS` | 260 ms | 停下多久恢复淡入 |
| `KEEP_PREFETCHED` | 10 | 持有几张预载 `Image` 引用（**不能删**：JS 不持有就丢 `ImageResourceContent`，解码缓存条目一起失效，上屏会从 11 ms 退到 1.4 s） |
| 窗口 padding | 前 1 后 2 | `from = first-1, to = last+2` |
| 打底档位 | 720 | `getBestSizedMediaPath(720,720)`，实测 ~40 KB/张（webp） |
| 原图 | `getOriginalMediaPath()` | 直出原文件，大图可到 79 MB |

**还能再快、但会牺牲画质的一条**（没做，等确认）：竖图流是 `object-fit: contain` 铺满视口，
屏幕上最多 2560 px 宽，却在下 8000 px 宽的原图。若把超大的图（`metadata.size.width > 4000`）
改走 `getBestSizedMediaPath(1440, 2560)`，体积约降到 1/10、解码位图从 ~190 MB 降到 ~8 MB，
滚动会更快更稳。代价：① 服务端首次要现生成这一档（实测冷生成 4.3 张/秒，会卡）；
② 放大会变软。要做得先批量预生成 1440 档。

现网 `pigallery2xin` 实际是**只读挂载**（config / db / tmp 都是 `ro`），切换命令按 `docker inspect` 的真实参数写：

```bash

sudo docker run -d --name pigallery2xin \
  -e TZ=Asia/Shanghai -e PUID=1000 -e PGID=1001 \
  -e NODE_ENV=production -e PG2_TLS_HOST=192.168.0.10 \
  -e Photo_photoLoadMethod=Original \
  -e default-Database-dbFolder=/app/data/db \
  -e default-Media-folder=/app/data/images \
  -e default-Media-tempFolder=/app/data/tmp \
  -e default-Extensions-folder=/app/data/config/extensions \
  -e PI_DOCKER=true \
  -v /vol1/1000/docker/pyxin/config:/app/data/config:ro \
  -v /vol1/1000/docker/pyxin/data:/app/data/db:ro \
  -v "/vol2/1000/图库/photo":/app/data/images \
  -v /vol1/1000/docker/pyxin/tmp:/app/data/tmp:ro \
  -p 8282:80 -p 8284:443 --restart unless-stopped ffvz/pigallery2:1.3.9
```
