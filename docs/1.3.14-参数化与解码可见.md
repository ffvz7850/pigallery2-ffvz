## 二、参数三层取值（任何一层缺失都不影响其它层）

```
内置默认 FLOW_DEFAULTS
   ↓ 覆盖
Config.Gallery.flow*  ← 设置页 @ConfigProperty（全局，跨设备）
   ↓ 覆盖
localStorage['vf.tune.v1']  ← 诊断面板（本机、即时、刷新保留、一定可用）
```

**为什么不平铺成一层**：这个镜像只换 `dist`，后端不重建。设置项写在 `ClientGalleryConfig` 里，服务端若还用旧编译产物，就既不认识这些字段、也不会下发 —— 设置页能看能改、保存后却回不到前端。所以 localStorage 必须是独立的一层，不能当"补充"。

本轮已把编译后的 `ClientConfig.js` 同步进镜像（见第六节），三层现在都是通的；但保底设计保留 —— 以后换底座忘了同步后端，面板仍然可用。

## 四、两个新参数是怎么真的生效的

### 1) 原图预缓存张数 = 硬上限，不是「距锚点几张」

```ts
// 只保留离锚点最近的 K 张，其余释放
if (this.prefetchImgs.size <= this.tuning.fullKeep) return;
const byDist = [...keys].sort(按 |i - anchorIdx| 升序);
const keep = new Set(byDist.slice(0, this.tuning.fullKeep));
// 其余的 delete —— fetched 仍为 true，不会重新下载
```

释放掉的是 **JS 对解码位图的持有**，不是文件（文件在 HTTP 缓存里，`fetched` 仍为 true）。等价于给原图划了一个内存上限，剩下的解码缓存预算自然留给 720p。

> 修了一个 bug：这个上限原先只在「窗口变化」时裁一次。稳态下窗口不动、预载陆续完成，数量会悄悄超过 K（实测刷新后出现 `6/5`）。现在 `markDownloaded()` 里也裁一次，`k/K` 永远 ≤ 1。

### 2) 720p 预上屏 = 两个窗口

```
原图窗口： first-mountBehind  …  last+mountAhead
底图窗口： first-mountBehind  …  last+thumbMountAhead   (≥ 原图窗口)
```

多挂出来的项标 `thumbOnly: true`，模板里**只渲染 `<img class="vf-bg">`**，不渲染 `.vf-full`、不渲染视频封面/播放键：

```html
<ng-container *ngIf="!w.thumbOnly && w.item.gridMedia.isPhoto()">
  <img class="vf-full" ...>
</ng-container>
```

所以它们几乎不吃内存，却能在原图完全跟不上时保证「滑到哪儿都有图」。

并且预热范围也跟着扩到 `max(to + thumbAhead, winThumbTo)` —— 多挂出来的项同样提前 download + decode，不是等挂载才发请求。

默认 `thumbMountAhead = mountAhead = 2`，**与 1.3.13 行为完全一致**；只有调大才出现 thumbOnly 项。

## 五、解码状态可见

`FlowItem` 加了两个只读标记（调度逻辑一律不看）：

- `stage`：`idle → downloading → decoding → decoded → shown`，异常时 `aborted` / `failed` / `released`
- `thumbStage`：`idle → downloading → ready / failed`

之前的 `decode()` 是 fire-and-forget，「文件到手」被当成「已经能上屏」。现在把 Promise 的结果记下来：

```ts
img.decode().then(() => { item.stage = 'decoded'; stats.decodeDone++; })
          .catch(() => { item.stage = 'failed'; stats.decodeFailed++; });
```

诊断条长这样：

```
窗口 4 / 底图多挂 4 · 原图保活 5/5 · 下载中 0 / 底图 0 · 720p 上屏 8/8
· 解码完成 6 失败 0 · 掐断 0 释放 1
decoded:6  idle:334  shown:4
```

怎么读：

| 字段 | 含义 | 异常信号 |
|---|---|---|
| 原图保活 k/K | 当前持有几张已解码原图 / 上限 | k 长期 = K 且 720p 上屏下降 → 调小 K |
| 720p 上屏 r/n | 当前挂载项里底图已可绘制的比例 | < 100% 说明预热没追上，调大 thumbAhead / thumbSlots |
| 解码完成 / 失败 | 累计成功 / 失败 | 失败持续增长 → URL 或服务端问题 |
| 掐断 | 被 `abortStale` 取消的下载数 | 甩动时增长正常，静止时增长说明窗口在抖 |
| 释放 | 被 `trimPrefetch` 放掉的张数 | 大幅增长 = K 太小，反复丢解码成果 |

顺手修的第二条不可靠断言：`thumbWarmed` 原来在**发起请求时**就置 true，请求被中断或位图被驱逐后这一项永远进不了待办，底图再也补不回来。现在改成「下载 + decode 都完成」才置位。

## 六、设置项为什么需要同步后端一个文件

现象：设置页显示 8，改成 9，点保存，刷新回到 8。

原因：`@ConfigProperty` 只是**渲染**设置页；值要通过 `PUT /pgapi/settings` 存进 `config.json`，再由服务端把 `ConfigInject` 注入首页。服务端用的是 `/app/src/common/config/public/ClientConfig.js` 这份**编译产物**——只换 `dist` 的话它还是旧版，不认识 `flowFullKeep`，于是存不进去、也下发不出来。

验证方法：

```bash
docker exec pigallery2flow grep -c flowFullKeep /app/src/common/config/public/ClientConfig.js
# 0 = 后端不认识
```

修法：Dockerfile 里多一行（`ClientConfig.js` 是 `npx tsc` 的产物，纯配置类，无业务逻辑）：

```dockerfile
COPY ClientConfig.js /app/src/common/config/public/ClientConfig.js
COPY dist /app/dist
```

改完实测：`config.json` 写入 7 个字段 → 灯箱诊断显示 `/9` → 改回 8 后显示 `/8`。**端到端通了。**

> 注意：这是"改后端"，但只换一个数据类编译产物，且只含我们自己的字段。以后换底座（`flat-xxxx`）时必须重新拷这份文件，否则设置项又变回摆设。

## 八、怎么用

**调参（推荐）**

1. 地址栏加 `?vfdebug`（或设置里打开"显示诊断条"）
2. 打开任意竖图，左下角出现面板
3. 拖滑块 → 立刻生效；看完关掉面板

**设置页**

**清空本机覆盖**

```js
localStorage.removeItem('vf.tune.v1')   // 或面板里点「恢复默认」
```

## 九、踩坑

1. **脚本 CRLF**：用 Python 改 `.sh` 时 `io.open(...,'w')` 在 Windows 会写成 CRLF，Linux 上 `set -e\r` 直接报 `invalid option`，且 `set -e` 失效导致后续语法错误被吞。改脚本后统一转 LF 并核 `data.count(b'\r\n') == 0`。
2. **`ssh_exec_file.py` 把 stderr 丢了**（`2>/dev/null`），脚本失败时看起来"跑完了但没输出"。已去掉这个屏蔽。
3. **设置页路由是 `/admin`**，不是 `/settings`（后者 404）。
4. **设置页保存按钮是 `[disabled]="!changed"`**：用 JS 直接改 `input.value` 不会触发 Angular 脏检测，必须走真实输入（`page.fill`）。
5. **把设置项写进 `ConfigPriority.underTheHood` 约等于「设置里没有」**：设置页默认只显示 `basic`。第一版就是这么翻的车 ——
   而且我用 `config-priority=3` 的 cookie 去验证，等于自己给自己开了后门，测出来「8 处可见」，用户那边一片空白。
   现在 7 项全部放 `basic`，**验证时必须不带 priority cookie**（`PRIO=1` 模拟默认）。
