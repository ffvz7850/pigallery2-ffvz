## 一、底图：从纯黑换成中性灰

`.vf-root` 和 `.vf-item` 原来分别是 `#000` / `#141414` —— 图片没到位时是一块纯黑，
和亮照片之间的落差太大，快速滑动时会被眼睛读成"闪一下黑洞"。

现在统一成一个 CSS 变量：

```css
:host { --vf-void: #2b2b2b; }   /* rgb(43,43,43)，中性灰（r=g=b），约 17% 亮度 */
.vf-root { background: var(--vf-void); }
.vf-item { background-color: var(--vf-void); }
.vf-video { background: var(--vf-void); }
```

为什么要**同一个值**用在根层和每一项：只要两处颜色不同，快速滑动或滚到列表两端时，
就会在两种灰交界处冒出一条边 —— 那比纯黑还显眼。统一之后，任何一帧、任何缝隙都是同一个色。

要调深浅只改 `--vf-void` 一个数：往 `#333` 走更亮（更像"暗房墙面"），往 `#1c1c1c` 走更接近原来的黑。

实测（把图片请求全部拖住，只剩底色）：

```
BG {"itemBg":"rgb(43, 43, 43)","rootBg":"rgb(43, 43, 43)","rootVar":"#2b2b2b"}
```

## 二、参数精简

### 1. 四套预载距离 → 一套（少两个常量）

原来是 `AHEAD_DOWN=6 / BEHIND_DOWN=2` 加 `AHEAD_UP=3 / BEHIND_UP=5`，四个常量配两套不对称策略。

实际上向上滑时"上面"那些图刚看过、`fetched` 已经是 true，`pump()` 会直接跳过不下载 ——
给它们 5 张的额度纯属多余。统一成：

```ts
const AHEAD = 6;   // 行进方向
const BEHIND = 2;  // 回扫方向
const downN = down ? AHEAD : BEHIND;
const upN = down ? BEHIND : AHEAD;
```

### 2. 删掉 `KEEP_PREFETCHED` 的 LRU 上限

原来 `holdImg()` 用 `Map + 最近 10 张` 保活预载过的 `Image`。问题是**这个上限按插入顺序淘汰，
并不保证留下的是"最该留的那几张"**，纯属拍脑袋的数字。

现在改成按需：预载 Image 只在"已下好、还没挂载"这个窗口里需要保活，
一旦挂载 DOM 的 `<img>` 自己就持有同一份资源。所以直接在 `refreshWanted()` 里按 `wanted` 释放：

```ts
this.prefetchImgs.forEach((_img, i) => {
  if (!this.wanted.has(i)) this.prefetchImgs.delete(i);
});
```

`holdImg()` 整个方法（12 行）随之消失，`markDownloaded()` 收敛成两行。
**这个引用不能省**：JS 一旦放手，`ImageResourceContent` 被回收，解码缓存条目一起失效，
DOM 挂载时就得重新解码整张原图 —— 实测会从 11 ms 退化到 1.4 s。

### 3. 另外两处小减法

- `isReady(index)` 方法只有一处调用 → 内联进 `pump()`，少一次函数调用 + 少 4 行。
- `refreshWanted()` 里的 `addThumb` 箭头函数**每次窗口变化都新建一个闭包** → 提成类方法
  `addThumbWanted(i)`，稳态下每帧少一次闭包分配。

## 三、参数现状（本轮调完）

| 位置 | 值 | 说明 |
|---|---|---|
| `AHEAD` / `BEHIND` | 6 / 2 | 行进方向 6 张、回扫 2 张（原为 4 个常量） |
| `MAX_DOWNLOADS` | 4 | 原图并发 |
| `MAX_THUMB_DOWNLOADS` | 6 | 打底图并发（独立通道，不占原图槽） |
| `THUMB_AHEAD` / `FAST_THUMB_AHEAD` | 2 / 12 | 静止 2 张，甩动扩到 12 张 |
| `FAST_SCROLL_RATE` / `FAST_SETTLE_MS` | 1.2 px/ms / 260 ms | 甩动判定与恢复 |
| `RESIZE_SETTLE_MS` | 140 ms | resize 防抖 |
| 打底档位 | 720 | `getBestSizedMediaPath(720,720)`，约 40 KB/张（webp） |
| `KEEP_PREFETCHED` | **已删** | 改为按 `wanted` 释放 |

**关于还能不能更快**：生产与测试都是 HTTPS → HTTP/2（实测 `v=2`），没有"每域名 6 连接"上限，
所以并发参数不需要为它让路。真正的瓶颈是原图本身（这个目录平均 5 MB，最大单张 79 MB）。
想再快只有一条路：对超大图改走 `getBestSizedMediaPath(1440, 2560)`（体积约 1/10），
但服务端首次要现生成（4.3 张/秒，会卡）且放大会变软 —— 本轮没做。
