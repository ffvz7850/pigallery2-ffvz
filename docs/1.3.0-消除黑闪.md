# 1.3.0 — 修复大图向下滑动时"黑一下再刷出来"

> 1.3.0 = 1.2.1（含 https/h2）+ 本次渲染修复。前端只改 flow 组件的 3 个文件，upstream 一行未动。
> 测试容器 `pigallery2flow`：`8285`(http) / `8286`(https)，现网 8282 未动。

---

## 一、根因不是网络，是渲染

先说清楚：这个黑帧跟 h2、跟带宽**没关系**，跟"图大"有关，是因为**解码时间**。

原来的实现有两处叠加：

```css
.vf-item { background: #000; }                /* ① 底是纯黑 */
.vf-item img { opacity: 0; transition: opacity 0.12s linear; }  /* ② 淡入 */
.vf-item img.vf-ok { opacity: 1; }
```

竖图流是**虚拟滚动**——滚出窗口的 `<img>` 会被销毁，滚回来时重新创建。触发链：

1. 新 `<img>` 节点插入，`opacity` 从 0 开始 → 那 0.12s 里它还没显示；
2. 同时浏览器要重新解码这张原图（大图解码产物是原图尺寸的位图：一张 6000×4000 的 JPEG 解码后约 96MB 内存，很快就会把 Chrome 的解码缓存挤爆，所以"看过"的图仍可能要重新解码）；
3. 解码完成的这几帧里，`<img>` 透明、底下是 `#000` → **纯黑**；
4. 解码一完成，因为是本地缓存，**瞬间**就出来了。

于是就成了"黑一下 → 瞬间刷出来"。图越大，第 2 步越久，黑得越明显——完全对应你的观察。

## 二、改法

### 1. 用网格里已缓存的缩略图当底图（关键是**零额外请求**）

`.vf-item` 的背景图直接指向**网格当时加载过的那个缩略图 URL**（同一个 URL → 浏览器缓存命中，不发新请求）：

```ts
public bgOf(item: FlowItem): string {
  if (!item.gridMedia.isPhoto()) return null;
  const thumb = item.thumbPath || (item.thumbPath = item.gridMedia.getThumbnailPath());
  return thumb ? 'url("' + thumb + '")' : null;
}
```

```html
<div class="vf-item" ... [style.background-image]="bgOf(w.item)">
```

```css
.vf-item {
  background-color: #0b0b0b;
  background-repeat: no-repeat;
  background-position: center center;
  background-size: contain;   /* 和 object-fit: contain 对齐，不变形 */
}
```

这样任何一帧都有东西可画：先看到**略模糊的照片**，原图解码完再瞬间替换，视觉上只是"清晰了一下"。

### 2. 去掉 0.12s 淡入

`img` 的 `opacity` 过渡删掉。现在 `loaded` 只在 `img.decode()` resolve 之后才置 true，替换是**原子**的：模糊 → 清晰，中间不经过"半透明叠在黑底上"的那种发灰。

## 三、实测（可复现的对照实验）

headless 的 screencast 会丢帧（1.4s 只出 15 帧），抓不到 1~2 帧的瞬黑，所以改用**确定性实验**：用 Playwright 拦截请求，把**原图延迟 3 秒**（缩略图正常放行），然后滚到未加载区域截图——此时屏幕上画的是什么，就是用户看到的什么。

| 版本 | 延迟的原图请求 | 帧平均亮度 | 近黑像素占比 | `<div class=vf-item>` 背景 |
|---|---|---|---|---|
| **1.2.1（旧）** | 9 | **0.0** | **100%** | `none`（纯黑） |
| **1.3.0（新）** | 9 | **151.5** | 10.9% | `thumb`（缩略图） |

旧版是**整屏纯黑**（亮度 0.0 / 100% 黑像素），新版显示照片内容（略模糊）——就是本文档目录里那两张 `placeholder-old.png` / `placeholder-new.png`。

其余回归项：竖图流 `3 / 36` 计数正常、5 个 DOM 节点、点击隐顶栏、Esc 退出、https 仍为 h2（`v=2`）、无控制台报错。

## 四、顺带说明：h2 那版要不要留

你反馈"看样子没区别"，这是符合预期的——h2 只解决**请求排队**，不解决**解码空窗**。它的价值在于：

- 预载不再抢可见图的连接名额（弱网/大图连读时才有体感）
- 顺带拿到 https（`pigallery2-lang` cookie 在 http 下会丢的老问题自动消失）

如果觉得不值那 50MB，我可以另出一个**不带 caddy 的 1.1.7**（= 1.1.6 + 本次渲染修复），compose 一行都不用改。
