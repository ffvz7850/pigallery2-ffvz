# 1.3.3 — 预载调度重构（让"下一张"永远先就绪）

> 基线：`ffvz/pigallery2:1.3.2`（视频海报预热）。
> 只改 `flow/` 组件，upstream 零改动。测试容器 `pigallery2flow`：`8285`(http) / `8286`(https)。

---

## 一、审查：旧实现为什么"下一张"抢不上

原来的预载是 **只往后追加的 FIFO 队列**，问题不在 decode，而在**调度**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `prefetchQueue` 是只进不出的数组，`prefetched` 集合永不淘汰 | 快速滑动时队列里堆满**早已划过去**的图，pump 还按老顺序一张张下 |
| 2 | 入队顺序固定 `to+1 → to+3`，再 `from-1` | 不区分"下一张"和"第八张"，最该先好的排在后面 |
| 3 | 下载与解码共用 `PREFETCH_CONCURRENCY = 2` 一个槽 | 解一张大图的几十毫秒里，**后面的图连请求都发不出去** |
| 4 | 方向无关：`AHEAD 3 / BEHIND 1` | 往回翻时只备 1 张，回翻必然露白 |
| 5 | 无中止机制 | 甩动时过期请求继续占着连接和带宽 |
| 6 | `item.decoded` 只在预载路径设置；挂载后自己加载完的项永远不标 | 每次滚动都被当成"待预载"，**重复下载 + 重复解码** |

第 6 条尤其隐蔽：`<img>` 挂载后由 `reveal()` 设的是 `loaded`，不是 `decoded`，于是 `isReady` 永远为假。

## 二、新设计

### 1. 从"队列"改成"快照"（`refreshWanted`）

每次滚动都重算一份"当前该备哪些"的集合，而不是往后追加：

```ts
for (let i = to + 1; i <= min(n-1, to + ahead); i++) next.add(i);   // 前方
for (let i = from - 1; i >= max(0, from - behind); i--) next.add(i); // 后方
this.wanted = next;
this.abortStale();   // 掉出集合的 → 直接掐掉请求
```

- 挂载窗口内（`from..to`）**不进集合**：它们已经躺在 DOM 里，浏览器自己在下（Safari 对同 URL 的 in-flight 请求不合并，放进去会白下两遍）
- `ahead / behind` 按方向切换：向下 `6/2`，向上 `3/5`

### 2. 锚点优先排序

```ts
this.anchorIdx = down ? last : first;   // 向下取屏底，向上取屏顶
cands.sort((a, b) => Math.abs(a - anchor) - Math.abs(b - anchor));
```

用屏底而不是屏中心：向下滑时 `anchor+1` 才是真正意义上的"下一张"，它必须第一个被下载。

同时紧挨锚点的那张给 `fetchPriority = 'high'`，其余 `'low'`。

### 3. 下载 / 解码分槽

```ts
const MAX_DOWNLOADS = 4;   // IO 并行放宽
const MAX_DECODES = 2;     // 解码收紧，别把主线程占满
```

```ts
img.onload = () => {
  this.inFlight.delete(index);
  this.holdImg(index, img);
  this.enqueueDecode(index, img);
  this.pump();          // 下载槽一空就接着下一张，不等解码
};
```

解码队列按"离锚点距离"插队，最近的那张永远先解。

### 4. 中止过期请求

```ts
private abortStale(): void {
  this.inFlight.forEach((img, i) => {
    if (this.wanted.has(i)) return;
    img.onload = null; img.onerror = null;
    img.src = '';                    // 中止
    this.inFlight.delete(i);
  });
}
```

### 5. 修掉 decoded 标记漏设

```ts
private reveal(item, img): void {
  const show = () => {
    item.loaded = true;
    item.decoded = true;   // ← 挂载后自己加载完的同样算"已解码"
    ...
  };
}
```

不补这一行，滚过的图每次回来都会重新预载一遍。

### 6. 解码位图持有量封顶

```ts
const KEEP_DECODED = 10;   // 一张 6000×4000 解码后约 96 MB，不能"全留着"
```

`holdImg()` 把刚完成的挪到 Map 末尾，从头淘汰最旧的。

## 三、参数一览

| 常量 | 值 | 说明 |
|---|---|---|
| `AHEAD_DOWN` / `BEHIND_DOWN` | 6 / 2 | 向下滑 |
| `AHEAD_UP` / `BEHIND_UP` | 3 / 5 | 向上滑 |
| `MAX_DOWNLOADS` | 4 | 并行下载数 |
| `MAX_DECODES` | 2 | 并行解码数 |
| `KEEP_DECODED` | 10 | 保留解码位图的张数 |

## 四、A/B 实测

方法：Playwright + Edge 1280×900，`page.route` 给**原图**加 600 ms 延迟（局域网太快，不加延迟任何版本都是 100%，没有区分度），
用 `MutationObserver` 记录每个 `.vf-item` 插入 DOM 的时刻，再用 rAF 轮询它何时拿到 `.vf-ok`，两者之差就是"挂载 → 上屏"耗时。

**场景 A：正常手速**（每屏停 550 ms，下 6 屏 + 回翻 4 屏）

| 版本 | 挂载次数 | 立即上屏（≤50 ms） | p50 | p90 | max |
|---|---|---|---|---|---|
| 1.3.2 | 14 | 14/14 | 11 ms | 12 ms | 12 ms |
| 1.3.3 | 14 | 14/14 | 12 ms | 27 ms | 27 ms |

正常手速下两版都够用 —— 因为窗口本身提前挂载了 2 张。

**场景 B：惯性甩动**（每次跨 3 屏、90 ms 一次、连甩 5 次，跨约 8 张图）

| 版本 | 挂载次数 | 立即上屏 | p90 | max | 明细（ms） |
|---|---|---|---|---|---|
| 1.3.2 | 14 | **9/14** | 1696 | **2878** | 10,10,11,11,11,**1195,1195**,23,**1586,1696,2878**,11,11,12 |
| 1.3.3 | 14 | **12/14** | 473 | **809** | 10,10,12,12,12,12,12,10,11,**473,809**,12,12,12 |
| 1.3.3 复测 | 14 | 13/14 | 22 | 185 | — |
| 1.3.3 复测 | 14 | 12/14 | 568 | 739 | — |

- 慢挂载从 **5 张（最长 2.9 秒）** 降到 **1~2 张（最长 0.8 秒）**
- 剩下的 1~2 张是跨 8 张图甩动的物理极限（请求已在路上、只是没下完），不再是"没开始"
