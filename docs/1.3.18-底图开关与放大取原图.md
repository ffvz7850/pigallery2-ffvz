## 二、为什么"停手还要等一会"只有预热能解

冷生成一张 2160 的耗时是**解码本身**占大头，换档位换编码都省不掉：

```
decode-only          2505 ms
decode + resize-2160 2026 ms   ← 8736÷2160 ≈ 4.04，正好命中 JPEG 的 DCT 1/4 缩小解码
1440                 8603 ms   ← 反而更慢
1080                 9153 ms
```

也就是说：**只要你停下来才发请求，这 2.5 秒就一秒都省不掉。** 唯一的路是"在你还在看这张的时候，把下一张做完"。

1.3.17 把预热设成 0 是当时为了压 CPU（怕和 720 底图抢），代价就是这次的体感。
现在预热回来了，但用三条规则把 CPU 按住：

1. **服务端留位**：预热请求带 `X-Pg2-Pregen: 1`，`acquire()` 里 `limit = MAX_CONCURRENT - 1`。
   于是"要上屏的那张"永远抢得到名额，不会排在预热后面。
2. **单路预热**：`PREGEN_CONCURRENCY = 2 → 1`。单张 2.5 s，看一张图的两三秒刚好够做完下一张。
3. **会 abort**：换锚点、开始甩动、改参数时 `AbortController.abort()`。
   服务端 `acquire()` 每 40 ms 检查 `req.destroyed`，排队中的预热立刻让位（正在渲染的会把结果放进内存缓存，不白做）。

实测（`cpu_probe.py`，甩 8 屏）：

```
1.3.16  peak=334%  avg=53%
1.3.17  peak=100%  avg=12%
1.3.18  peak=197%  avg=33%   ← 峰值来自"甩动 + 预热"撞一起，6 s 后回落到 0
```

峰值抬头是预热换来的，但**只抬到 2 个 sharp 任务**（一个交互 + 一个预热），离 1.3.16 的三个半核还差得远，而且只发生在有活可干的那几秒。

## 三、720 底图开关：省的是什么

关掉后竖图流完全不请求 `getBestSizedMediaPath(720,720)`：

- 挂载窗口里每张一次 **JPEG 解码 + 一次栅格化**（720 档约 20~40 ms/张，甩动时是一串连着来）
- 每张约 120 KB 的带宽

代价写在设置项描述里了：**滑到新的一张时先看到底色**。所以关掉时建议把预热设到 2 以上 ——
两张配起来才是"省 CPU 又不空窗"的组合：底图不挂 → 省解码；预热提前做 → 换图时高清档已在服务端内存里。

> 现网 `pyxin/config.json` 里本来就没有 `flowLowEnabled`，所以切到 1.3.18 后**默认是开**（保持原样），
> 想省 CPU 到设置 → 画廊 → 「竖图流 · 加载 720 底图」关掉即可。顺便发现现网 `flowPreGen` 已经是 2（你自己调过），新版正好沿用。

## 四、双指放大取原图

竖图流的"放大"用的是**浏览器原生缩放**（`index.html` 只有 `initial-scale=1`，没禁 `user-scalable`），
所以这里不自己实现一套 transform 缩放 —— 那会和竖向滚动抢 touchmove，得不偿失。只监听"放大发生了"这一件事：

```ts
// 1) 标准做法
visualViewport.addEventListener('resize', () => {
  if (visualViewport.scale > 1.05) this.escalateToOriginal();
});

// 2) 兜底：没有 visualViewport 的 webview
onPinchMove(e) { if (span(e.touches) / this.pinchDist > 1.12) this.escalateToOriginal(); }
```

`escalateToOriginal()` 只做一件事：把当前这张的 `hdPath` 换成 `getOriginalMediaPath()`。
**只升不降** —— 原图下下来就留着，松手缩回去再放大不用重来（离开窗口自然会随 DOM 释放）。

为什么值得：2160 档在原生 2~3 倍放大下就是虚的，而原图是磁盘上现成的 JPEG，
不需要服务端再算什么 —— 放大这一步本来就是要"看清细节"，这时再省流量没意义。
