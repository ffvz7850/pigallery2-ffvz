## 一、卡顿定位：主色取色把主线程堵死了

### 测量方法

新建 `pg2-test/jank_probe.js`：

- CDP `Performance.enable` 取 `ScriptDuration / LayoutDuration / RecalcStyleDuration / TaskDuration` 的增量；
- `PerformanceObserver('longtask')` 统计主线程长任务；
- 页面内 rAF 记录帧间隔；
- `Emulation.setCPUThrottlingRate(4)` 放大 CPU 瓶颈（否则本机太快、看不出差异）；
- patch `CanvasRenderingContext2D.drawImage / getImageData` 和 `document.createElement('canvas')` 计数并计时；
- `page.mouse.wheel` 连续滚 40 次 × 220px，模拟真实滚轮。

### 1.3.7 的实测结果（344 张目录，深处，4× 降速）

```
FRAMES frames=149 avgGap=21.6 p95=71 max=391.8 over25=16 over50=14
       longTasks=12 longTaskMs=699 longMax=67
COST   scriptMs=411 layoutMs=9 styleMs=7 taskMs=2267
CV     draw=20 drawMs=9.5  gid=20  gidMs=985.9  canvas=20
```

**`layoutMs 9` / `styleMs 7` 说明跟布局、重绘、合成层无关；`scriptMs 411` + 20 个 longtask 说明卡在 JS 主线程。**

而 `getImageData` 20 次累计 **985.9 ms**（单次约 49 ms），`drawImage` 只用 9.5 ms。**主色取色就是元凶。**

### 一次误判与纠正

第一反应是"GPU 同步回读"，于是改成复用一块 canvas + `getContext('2d', {willReadFrequently: true})`。

重测：`gidMs` 仍是 **1090 ms**，没有改善。

于是写了个不依赖构建的基准 `pg2-test/canvas_color_bench.js`，在同一张 720p 缩略图上比较四种写法：

| 写法 | 耗时 |
|---|---|
| A 每次新建 canvas + 1×1 | ≈12 ms |
| B1 复用 canvas + willReadFrequently（**首次**画这张图） | **11.8 ms** |
| B2 同一张图**第二次**画 | **0 ms** |
| C 缩到 8×8 再求平均 | 0.5 ms（同一张图的第二次） |
| D `createImageBitmap(resizeWidth:1)` | 12 ms（异步） |

**结论**：成本不在 `getImageData`，也不在 canvas 初始化，而在**每一张新图首次 `drawImage` 到 canvas 时的上传/栅格化**，约 12 ms/张（4× 降速下 ~48 ms，正好对上实测）。复用 canvas 只能省掉"同一张的第二次"，省不掉每张的第一次。

所以这笔钱**无法消除，只能挪出滚动路径**。

## 二、按你的要求：不生成图片占位

你说的"像手机状态栏那样自适应、不生成图片占位"，我按这个执行：**彻底放弃按图取色**。

理由：真正的"按图片明暗自适应"仍然要读一次像素，成本和取平均色一样（12 ms/张），只是换个算法；要做到零成本，只能不读像素。

所以改成：

- 删除整套取色：`paintDominant / queueDominant / scheduleDominantIdle / cancelDominantIdle / scheduleFlush / dominantOf`、`domCtx / domQueue / domIdle / dominantRaf`、`FlowItem.dominant`、模板里的 `[style.background-color]` 绑定。
- 兜底统一为 `.vf-item { background-color: #141414 }`（比灯箱 `#000` 略亮，视觉是"暗场"不是"黑洞"）。
- 真正的占位仍然由**常驻的 `.vf-bg` 720p 缩略图**负责——它本来就在，不需要额外生成任何东西。

> 如果你后面确实想要"亮图浅底 / 暗图深底"，那必须有像素数据。可行的低成本做法是只取亮度、放进 Worker 用 `OffscreenCanvas` 处理，主线程零阻塞；但代码量和维护成本都会上去，这版没有做。

## 三、顺带精简与优化（都是滚动路径上的实活）

| # | 改动 | 原因 |
|---|---|---|
| 1 | `updateWindow` 窗口未变时**直接 return**，不再调 `refreshWanted` | 原来每帧都重算 Set、遍历 `inFlight`、`trimThumbs`、`pumpThumb`，而窗口其实要跨过一整屏才变；预载推进本来就由 `onload` 回调驱动 |
| 2 | `thumbWanted / thumbPriority` 改为**每帧重建**（`clear()` 后重新加） | 原来只增不减，滚得越久集合越大，每帧遍历+排序的代价跟着涨 |
| 3 | 删 `thumbImgs / trimThumbs / holdThumb / KEEP_THUMB_DECODED` | `.vf-bg` 常驻 DOM 已经持有缩略图位图，离屏再保活一份是重复的 |
| 4 | 删 `primeThumbs` 与 `PRIME_AHEAD / PRIME_BEHIND` | 与 `refreshWanted` 的范围重复，打开时 `updateWindow(true)` 已覆盖 |
| 5 | `.vf-bg` 去掉 `will-change: transform`，只留 `translateZ(0)` | `will-change` 表示"这个属性将要变化"，这里 transform 永远不变，只会让层常驻显存 |
| 6 | `zoom` 在 100% 时不再写 `zoom: 1`（绑 `null`） | 避免无谓进入 zoom 的布局分支 |

**代码量：TS 1052 → 940 行（-112 行，约 10.6%）。**

## 六、遗留与风险

1. **不再有按图主色**：可见槽位的兜底从"图片平均色"退成统一深灰 `#141414`。缩略图到位后由 `.vf-bg` 覆盖，实际观感影响只在"缩略图尚未到达"的几十毫秒。
2. **"自适应"没做到按图**：需要读像素，与"零成本、不生成占位"互斥；如需按图明暗，建议 Worker + `OffscreenCanvas`。
3. `thumbWanted` 每帧重建，意味着滚出视野的缩略图预热会被撤销；实测深处打底仍 100%，未观察到退化。
4. 第二次测量里出现过一次 `max 329.6 ms` 的单帧，`longTasks` 为 0，判断是首帧/冷启动而非滚动期，样本不足未深究。
