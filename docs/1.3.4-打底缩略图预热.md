# 1.3.4 — 打底缩略图（720）独立预热：滚到深处也不再黑

> 基线：`ffvz/pigallery2:1.3.3`。只改 `flow/` 组件。
> 测试容器 `pigallery2flow`：`8285`(http) / `8286`(https)。

---

## 一、现象与根因

用户反馈：**720 的缩略图并没有打底，只有前几张有效，之后还是会黑屏加载。**

根因有两条，都是"预热时机"而不是"有没有预热"：

### 根因 1：缩略图预热被原图下载槽卡住

`warmThumb()` 原来只在两个地方调用：

| 调用点 | 时机 | 问题 |
|---|---|---|
| `updateWindow()` | 窗口内项**已经挂载**那一刻 | 零提前量，`background-image` 本身也在这一瞬间才开始拉 |
| `startDownload()` | 轮到这张的原图**开始下载**时 | 原图只有 `MAX_DOWNLOADS = 4` 个槽 → **第 5 张以后要等前 4 张原图下完才开始下缩略图** |

所以前几张（网格里已经渲染过、HTTP 缓存里有）能打底，之后就是纯黑等原图。

### 根因 2：档位用的是网格渲染尺寸

`thumbOf()` 原来走 `gridMedia.getThumbnailPath()`，它用 GridMedia 创建时的**网格渲染尺寸**算档位。
竖图流滚到深处的项当初根本没在网格里渲染过，`renderWidth = 0`，算出来的档位不可靠。

（本站配置 `thumbnailSizes = [720]` 只有一档，所以碰巧仍能拼出 `/720`；换一份多档配置就会拼错。）

## 二、改法

### 1. 缩略图独立一条通道

```ts
const THUMB_AHEAD = 10;          // 比原图备得更远
const MAX_THUMB_DOWNLOADS = 4;   // 自己的并发，不跟原图抢
```

```ts
private pumpThumb(): void {
  // 范围：挂载窗口之后 to+ahead+10 张（约 16 张 / 8~16 屏）
  // 排序：离锚点越近越先下（与打底相关的只有"快要看到的")
}
private startThumb(index: number): void {
  item.thumbWarmed = true;
  this.thumbInFlight.add(index);
  const im = new Image();
  im.fetchPriority = 'auto';       // 打底图是"别让我看到黑"的唯一保障，不能排最低
  im.onload  = () => im.decode?.().then(done).catch(done) ?? done();
  im.onerror = () => { item.thumbWarmed = false; this.thumbFailed.add(index); done(); };
  im.src = this.thumbOf(item);
}
```

要点：
- **不占原图的 4 个下载槽**，可以远早于对应原图开始准备
- `decode()` 后才算完成，挂上 DOM 就是现成位图
- 失败**不永久放弃**（`thumbWarmed` 复位），下次滚动再试

### 2. 档位改成固定的 720

```ts
private thumbOf(item: FlowItem): string {
  return item.thumbPath ||
    (item.thumbPath = item.gridMedia.getBestSizedMediaPath(720, 720));
}
```

不再依赖 `renderWidth`。720 档刚好够满屏"糊底图"的清晰度，单张 45~190 KB，能一口气预热十几张。
`onResize()` 时连同 `posterPath` 一起清掉重算。

### 3. 窗口内不重复预热

`refreshWanted()` 里算 `thumbWanted` 时只放**窗口外**的项：窗口内的 `.vf-item` 已经在 DOM 里，
`background-image` 由浏览器自己拉，再 `new Image()` 一次在 Safari 上会白下两遍。

## 三、实测

场景是关键：**小目录测不出问题**。目录只有 28 项时，滚两下就到底，预热早就全覆盖了（1.3.3 也是 100%）。

必须滚到一个**几百张的大目录的深处**——那里的缩略图从来没被网格渲染过：

- 目录：真实图库里的 344 张套图
- 先连续滚 40 屏（约第 13~20 张），再从零开始统计
- 缩略图请求人为加 1500 ms 延迟（模拟服务端现生成 / 慢链路）
- 指标：每个 `.vf-item` 挂载那一刻，它的 `background-image` 是否已经 `responseEnd`

| 版本 | 挂载时已打底 | 停止瞬间当前屏 | 说明 |
|---|---|---|---|
| 1.3.3 | **5/13（38.5%）** | 1/2 | 有 8 张挂载后 500~6600 ms 才下完，就是黑屏 |
| 1.3.4 | **13/13（100%）** | 2/2 | 全部提前 10~16 秒下载完 |
| 1.3.4 复测 | 12/12（100%） | 2/2 | — |
| 1.3.4 复测 | 13/13（100%） | 2/2 | — |

1.3.3 的失败样本（`gap` = 挂载时刻 − 下载完成时刻，负值表示"挂载后才下完"）：

```
-500, +6, +1142, +2930, +4890, +6576  (ms)
```

## 六、复现要点（下次别踩）

1. **必须用几百张的大目录**，且要先滚到深处（第 13 张以后）。28 项的小目录滚两下就到底，任何版本都 100%，测不出东西。
2. 缩略图请求要加延迟（1500 ms），否则局域网瞬间就下完，也测不出来。
3. 解析 `background-image` 不能用 `/url\("?([^")]+)"?\)/` —— **文件名里常有括号**（`xxx (Yiko).jpg`），正则会把它截断，导致所有 URL 都对不上 resource timing（表现为全部 `no-entry`）。
4. `performance` 的 resource 缓冲默认只有 250 条，缩略图一多就溢出，要 `setResourceTimingBufferSize(4000)`。
