# 1.3.17 — 分级加载：把 2160 的 CPU 从 334% 压到 100%

镜像 `ffvz/pigallery2:1.3.17`（929MB）
tar `/vol1/1000/docker/ffvz-pigallery2_1.3.17.tar`
测试容器 `pigallery2flow` 8285/8286 在跑。

---

## 一、现象与根因

现象：**滑动几张之后 CPU 占满，连 720 底图都卡。**

实测（`cpu_probe.py`，滑动 8 屏的同时每 0.4 s 采一次 `docker stats`）：

```
1.3.16：peak=334%  avg=53%   序列 0 0 6 19 9 0 74 32 0 291 137 334 331 313 174 90 0 ...
```

4 核上限是 400%，334% 等于**三个半核在烧**。

根因不是"2160 太重"，而是**并发数失控**：

1. `MemoryPreviewMWs` 是一条自己写的分支，**完全绕过了 PiGallery2 自己的生成队列**（`concurrentThumbnailGenerationsLimit` / `PhotoProcessing.taskQue`）。PiGallery2 本来有并发保护，我这条捷径把它跳过了。
2. 竖图流的挂载窗口是 4 张（视口 1 + 前 1 + 后 2），**每张都请求 2160**，于是 4 个 sharp 任务同时跑。
3. CPU 被吃满之后，Node 事件循环和磁盘 IO 一起被挤，720 请求（本该 16 ms 磁盘命中）也跟着变慢 —— 这就是"卡底图"。

---

## 二、四层修复

### 1. 服务端加闸门（最关键）

```ts
private static readonly MAX_CONCURRENT = 2;      // 同时最多 2 个 sharp
private static readonly QUEUE_TIMEOUT_MS = 8000; // 排太久就降级
private static readonly POLL_MS = 40;            // 顺便用来发现客户端已断开
```

- **命中内存不排队**（只有几毫秒），只有"要生成"才占名额
- 排队期间每 40 ms 检查 `req.destroyed` —— 滑过去 / 关灯箱的请求立刻放弃，不白烧 CPU
- 排队超过 8 s 直接降级：把**已有的 720 档**发回去，带 `Cache-Control: no-store`
  （不缓存，免得下次想要清晰版却命中糊图）

### 2. 只给"正在看的那张"生成 2160

```ts
public srcOf(w: FlowWindowItem): string {
  if (this.fastScrolling || w.index !== this.current) {
    return this.lowUrlOf(w.item);      // 720，已落盘，几十毫秒
  }
  return this.hdUrlOf(w.item);         // 2160，服务端现生成
}
```

旁边的图先给 720（**和底图是同一个 URL，浏览器只请求一次**，等于立即出图），滚到它时再升级。

配套：`updateWindow` 在"窗口没变但 current 变了"时也要刷一次，否则高清档永远追不上当前这张。

### 3. 甩动中一律 720

手指还在飞的时候，生成出来也没人看。甩动中全部走 720，停手后才升级 —— 和「延迟清晰化」是同一个思路。

### 4. 预热默认改成 0

有闸门之后，预热是在**抢当前图的名额**：它排在前面，反而让当前这张更晚。默认关掉。

## 三、实测对比

| | 1.3.16 | 1.3.17 |
|---|---|---|
| CPU 峰值 | **334%** | **100%** |
| CPU 均值 | 53% | **12%** |
| 高负载持续 | 约 2 s 内 5 个采样点 >170% | 只有 1 个点到 100% |
| 甩动后上屏 | `full 0/4`，3.5 s 才 1 张 | **`full 4/4` 立即全部上屏** |
| 720 底图 | 4/4（但被 CPU 拖） | 4/4 |
| 当前张清晰度 | 2160 | 2160（停手后升级） |

现在只剩**一个**任务在跑，只占一核，另外三核随便用。

## 五、观感变化（需要你确认）

- **旁边的图是 720**：它本来就在屏幕边缘或窗口外，滑过去 2.5 s 内升级成 2160。如果你希望"提前一张"就清晰，把设置里「预热张数」调到 1~2 —— 代价是 CPU 峰值回到 200% 左右。
- **升级时不淡入**：`.vf-full` 的 720 换成 2160 时 `loaded` 已经是 true，浏览器会保留旧图直到新图解码完，直接替换。下面一直压着 720 底图，所以不会黑、不会白，只是清晰度跳一下。
- **甩动中全是 720**：这是刻意的。停手就清晰。

## 六、设置项

`/admin` → 基础分组：

| 设置项 | 默认 | 说明 |
|---|---|---|
| 压缩档短边 | 2160 | 0 = 关闭，永远原图 |
| 预热张数 | **0**（1.3.16 是 4） | 调大能提前生成，但会抢当前图的名额 |

诊断条（`?vfdebug`）新增 `active` 计数，能直接看到服务端正在生成几个。

`GET /pgapi/gallery/preview-cache` 返回 `{items, bytes, active}`。

导出时发现 `pigallery2xin` 是 `Exited (0)`，8282/8284 都不通 —— 你的相册当时是断的。

要不要切到 1.3.17？切换命令见 1.3.16 文档第八节，把 tag 换成 `1.3.17` 即可；**必须用新镜像**（后端改了）。
