## 一、错在哪

1.3.18 我把"关掉 720 底图"实现成了：

```ts
// 1.3.18（错）
if (!isCurrent) {
  return this.tuning.lowEnabled ? this.lowUrlOf(w.item) : null;  // ← 非当前张直接不给图
}
```

`*ngIf` 把 `<img>` 整个摘掉 → 一屏只亮当前那一张，上下全是底色。滑过去就是黑的，
必须停手等 200ms + 现生成几百毫秒才有图。这是设计错了，不是参数问题。

## 二、改成什么

```ts
public srcOf(w: FlowWindowItem): string {
  const settled = !this.fastScrolling;
  const isCurrent = w.index === this.current;

  if (this.tuning.lowEnabled) {
    // 有底图：甩动中一律 720（省 CPU），停手后只有当前张升 2160 —— 1.3.17 的行为，不动
    return settled && isCurrent ? this.hdUrlOf(w.item) : this.lowUrlOf(w.item);
  }

  // 没底图：窗口里每张都得自己上屏，否则一屏只亮一张
  // 例外：甩动中只保"手指下那张"，其余等停手再要（挂上去的请求基本会被卸载，白下白算）
  return settled || isCurrent ? this.hdUrlOf(w.item) : null;
}
```

配套：`startPreGen()` 在关底图时直接返回 —— 挂载窗口已经在自己要高清档了，
再预热就是对着同一批 URL 重复下单，白占服务端名额。

CPU 依然有闸：服务端 `MAX_CONCURRENT=2`，队列里被放弃的请求 40ms 内被丢掉。
关底图时的代价是"一屏 3~4 张都要现生成"，这是没有占位图必然要付的钱。

## 三、验收（`v1320_test.js` 7/7）

用 100MP 那一档最狠的目录（`未压缩4/蠢沫沫 宴`，单张 65MB）测：

```
PASS 关底图：一张 720 都不挂                    nBg=0
PASS 关底图：窗口里每张都挂了 vf-full          nFull=3/nItem=3
PASS 关底图：挂的全是 2160                     hd=3 low=0
PASS 关底图：窗口内全部解码上屏                nFull=3/nItem=3 等待=2494ms
PASS 关底图：滑动后新窗口同样全部上屏          nFull=4/nItem=4 等待=939ms
PASS 开底图：底图回来了                        nBg=3
PASS 开底图：只有当前张走 2160                 hd=1 low=2
```

- 首屏 3 张 100MP 全上屏用了 **2.5s**（2 路并发，每张 ~2.4s 解码）
- 往后滑一张只需 **939ms**（只新增一张要生成）
- 开底图时行为完全没变（当前张 2160 / 其余 720）

回归：`v1318_test` 13/13（其中"关掉后非当前张不挂 vf-full"这条按新行为改成"窗口内每张都挂"）、
`v1319_test` 10/10、`v1317_test` 7/7。

## 四、现网状态

`pyxin/config.json` 里 `flowLowEnabled` 已经是 `false`（你在设置里关过），
所以切到 1.3.20 后直接就是"无底图 + 窗口全部上屏"的模式。想恢复 720 底图，
设置 → 画廊 → 「竖图流 · 加载 720 底图」打开即可。

**已知的小瑕疵**：诊断条在关底图时仍显示「预热 2 张」，实际上这时候预热是跳过的
（窗口自取已经覆盖）。不影响行为，下个版本顺手改掉。
