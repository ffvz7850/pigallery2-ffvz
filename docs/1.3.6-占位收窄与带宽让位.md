# 1.3.6 · 占位收窄到 3 张 + 带宽让位

> 上游零改动，只动 `flow/` 目录一个文件，替换前端 dist。
> 镜像 `ffvz/pigallery2:1.3.6`，测试容器 8285(http)/8286(https)，现网 8282 未动。

## 一、先纠正上一轮的判断偏差

上一轮我用"未生成缩略图"的图测出单张 450 ms，并据此说"下 2 张不够"。**那个测试环境是错的**：

| 目录 | 缩略图数量 | 说明 |
|---|---|---|
| 测试容器 `pg2flow/tmp` | **1,928** | 只有我测试过的图，近乎空缓存 |
| 现网 `pyxin/tmp` | **397,435** | 全库 390,726 张图，全部预生成，21 GB |

实测覆盖率为 100%（抽查 486/486、445/445、348/348、462/462、408/408），命名 `_720q80cs.webp`。

**在你的真实环境里，单张是磁盘命中 16 ms，4 并发 83 张/秒** —— 而快速甩动只消耗 11 张/秒。
补给是消耗的 7.5 倍，3 张缓冲完全够，上一轮那个"450 ms 追不上"的结论不成立。

因此本版把测试容器的 `-v` 从 `pg2flow/tmp` 改成 `pyxin/tmp`，**测试环境与真实环境一致**，下面所有数据都是在这个前提下测的。

## 二、改动（5 处）

| # | 改动 | 原因 |
|---|---|---|
| 1 | `THUMB_AHEAD` 10 → **2** | 挂载窗口本身已向下多挂 2 张，再加 2 张 = 约 4 张就够 |
| 2 | `PRIME_AHEAD` 8 → **2**、`PRIME_BEHIND` 2 → **1** | 打开即占位 = 当前 + 下 2 + 回退 1 |
| 3 | 删除 `scheduleIdleFill()` / `idleFillBatch()` / `cancelIdleFill()` 及游标字段 | 取消全量 720 预取：39 万张永远铺不完，且会稀释请求优先级 |
| 4 | 缩略图范围 `to + ahead + THUMB_AHEAD` → `to + THUMB_AHEAD` | 原来被叠加放大到 16 张，与"占位 3 张"的意图不符 |
| 5 | 原图 `fetchPriority` 恒为 `'low'` | 原图只负责"清晰"，不负责"不黑"；4 MB 的原图不该抢在 40 KB 打底图前面 |

保留不动：双通道独立（`MAX_THUMB_DOWNLOADS=4` 不占原图槽）、`.vf-bg` 常驻 + `.vf-full` 淡入、按滚动方向预取、位图封顶、甩动跳淡入。

## 三、验证（真实缩略图环境，https h2，目录 344 张）

```
OPEN     mounted=4   bgReadyFirst=4/4          ← 打开瞬间当前+下2+回退1 全部就绪
IDLE     灯箱内新增 720 请求 51 个 / 20 秒      ← 1.3.5 同目录 344 个，降 85%
SCROLL   40 屏 / 63 个可见槽位 / 打底率 100% / 0 屏有缺口
PRIORITY 原图 33 个 Low                         ← 原图不再抢带宽
```

回归：

| 项 | 1.3.5 | 1.3.6 |
|---|---|---|
| 滑动上屏即时率 | 12~13 / 14 | **14 / 14**（p50 11 ms，上下方向各 100%） |
| 视频海报 | 11/11 pre=pre | **11/11**，`post=0`，`decodedBefore=11` |
| 交互（计数 4/124、点画面隐顶栏、Esc、返回网格） | 全过 | 全过 |
| 控制台报错 | 3 条 | 同样 3 条（上游 `/pgapi/user/me` 401 + 两个 `console.error('OK')`，非本次引入） |

请求数从 344 降到 51，是本版最直观的收益：不再为整个目录预铺，只为眼前 3~4 张服务。

## 四、关于"通道不挤占"

- **逻辑层已经隔离**：缩略图有独立并发槽（4），原图另有下载槽（4），解码槽 2；缩略图请求不占原图的槽位。
- **带宽层靠体积差**：3 张 720p 约 120 KB，一张原图 3~5 MB，占比约 3%。
- **优先级层**：原图已全部降为 `low`。缩略图侧代码设 `fetchPriority='high'`（仅 `thumbPriority` 集合内的打开首批 + 窗口邻近），但用 CDP 抓 `Network.requestWillBeSent` 时 177 个缩略图请求全部报告为 `Low` —— Chromium 对离屏 `new Image()` 的优先级调整不体现在 `initialPriority` 上。**实测打底率 100%，说明靠体积差已经够，不依赖这个提示生效。**

## 五、已知限制

1. **新加入的图**（还没有生成缩略图）仍要 450 ms 左右。这时 3 张不够，会看到一段纯色块——需要主色兜底才能彻底不黑，本版没做。
2. 本版**没加主色占位**。缓存被清空、或请求失败时，`.vf-item` 底下仍是 `#0b0b0b`。
3. 镜像 1.12 GB，比 1.3.5 的 1.08 GB 多约 40 MB：`FROM 1.3.5` + `rm -rf /app/dist` + `COPY` 等于多留一份旧 dist 层。下版若从 1.3.2 一次成型可回到 1.08 GB。
4. `THUMB_AHEAD=2` / `PRIME_AHEAD=2` 是固定值，没有按网速/设备自适应。
