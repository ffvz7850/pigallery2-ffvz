## 二、为什么不能简单删掉短路

1.3.18 加短路时写的理由是「对同一批 URL 重复下单」。删掉之前先想清楚重复的代价：

```
关底图 → 挂载窗口里每张都在自己要高清档（fullSrcOf）
       → 预热又从同一批 URL 起
       → 服务端 MemoryPreviewMWs 只按「已生成」查缓存，没有 in-flight 去重
       → 同一张图跑两遍 sharp，CPU 直接翻倍
```

所以解耦的同时必须做两件事：

**① 起点推到窗口之后**：`firstIdx = current + 1 + mountAhead`

- 有底图：`firstIdx = from`（老行为，一个字节都没变）
- 无底图：跳过窗口内正在加载的那几张，只预热「滑过去还没人准备」的部分

**② 推迟到当前张上屏之后**（只对无底图）

服务端 `MAX_CONCURRENT = 2`，窗口里 3 张正在申请这两个名额。第一条预热如果这时插进去，
会实打实分掉一半并行度 —— 实测首屏 **4.6s → 5.0s（+400ms）**。

改成每 900ms 检查一次「当前张 loaded 没」：

- 普通图（生成 300~500ms）：很快 loaded → 预热几乎立刻开始，用户在看的这段时间刚好跑完
- 100MP 巨图（2.5s/张）：等首屏安静 → 首屏不受影响，预热在后续浏览的空隙里跑
- 最多等 6 轮（5.4s）就照跑，避免某张预览档生成失败把预热永久卡死

## 三、实测

### 冷态首屏（每次先清服务端预览缓存，各 2 次）

| | 首屏窗口内全部上屏 | 预热请求数 |
|---|---|---|
| `preGenCount=0` | 4715 / 4546 ms | 0 |
| `preGenCount=2`（延迟版） | **4269 / 4495 ms** | 1~2 |

延迟前那版是 5017 / 4825 ms —— **400ms 的代价已经拿回来了**（剩下的是噪声）。

### 解耦是否真的生效（无底图，100MP 目录）

```
打开后：nItem=3 nFull=3 窗口内2160=3 预热请求=2
PASS 预热请求真的发出去了（解耦生效）       pregen=2
PASS 预热 URL 与窗口内正在加载的 URL 不重叠  重叠=0
PASS 滚 3 屏后当前张已清晰                 等待=119ms
PASS 预热过的图被第二次请求时命中内存(<600ms) 样本=[[45,61],[2024,76]]
2160 请求耗时全样本: [45,61,70,76,130,153,2024]
```

对比延迟前那版：`[19,49,58,2305,2458,4566,4976,7168]` —— 最慢一笔 7.2s，就是因为预热和首屏抢名额。

## 四、顺带修的文案

`flowPreGen` 的设置项描述原来写「关掉底图时本项自动跳过」（批次 1 我写的，当时还是短路）。
已经改成真话：

> …关掉「加载 720 底图」时会自动跳过窗口内已在加载的那几张，只预热更后面的，不会重复生成。

> 注意：这条描述要**换镜像**才会在设置页显示。当前现网镜像 1.3.22 已含新文案，
> 但 `config.json` 里的 `//[flowPreGen]` 注释是历史值，只有下次在设置页保存才会刷新。
