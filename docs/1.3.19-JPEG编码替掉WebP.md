## 一、先回答三个问题

### 1. 你的图「基本都支持 DCT」吗？——不支持，只有 9%

图库实测（`/vol2/1000/图库/photo`，397755 个文件 / 1019GB）：

```
jpg 372228   jpeg 8108   png 9709   mp4 5269   gif 1128   webp 681   heic 24
```

JPEG 占 95.7%，格式不是问题。**问题是尺寸**：抽 160 张（其中 jpeg 153 张）测短边：

```
p10=1069  p25=1733  p50=3024  p75=3840  p90=4160  max=8000
```

DCT 只能 1/2、1/4、1/8，要做到 2160 档就得短边 ≥ 4320。按 p90=4160 算，
**能走 DCT 的只有 14/153 = 9.2%**。中位数 3024 的图根本够不着。

### 2. DCT 在你这套环境里生效了吗？——**压根没生效**

这一点比"支不支持"更要紧。拿那张 8736×11648 / 65MB 的图直接测（`dct_probe.js`，各 3 次取最小）：

| 做法 | 耗时 |
|------|------|
| 全解码（地板） | 2447 ms |
| 缩到 2160（现行，默认开 shrink-on-load） | **2240 ms** |
| 同一句**关掉** `fastShrinkOnLoad` | **2257 ms** ← 一样 |
| 精确 1/4（2184×2912，本该纯 DCT） | 2337 ms |
| 精确 1/8（1092×1456） | 2443 ms |
| 精确 1/2（4368×5824） | 6869 ms |

开/关一样、精确 1/4 也不快 —— 说明 libvips 每次都老老实实全解码再缩。
所以"优先 DCT"无从谈起，**这条线按你的判断划掉，不做了**。

### 3. 「jpg 压缩 jpg 更快」——对，而且是这次唯一的真收益

同一批真图，同一次运行里交错测（排除机器负载漂移）：

| 源图 | 全解码 | 现行 webp e2 | 改 jpeg q80 | 体积 webp → jpeg |
|------|--------|--------------|-------------|------------------|
| 3024×3024 (0.8MB) | 68 ms | **896 ms** | **176 ms** | 298 → 464 KB |
| 4000×6000 (2.9MB) | 194 ms | **1510 ms** | **423 ms** | 362 → 680 KB |
| 5792×8688 (7.6MB) | 423 ms | **1819 ms** | **757 ms** | 475 → 636 KB |

**瓶颈根本不是缩放，是编码器**：3024² 那张，896ms 里有 800ms 花在 libwebp 上，
换成 libjpeg-turbo 只要 100ms。稳定 2.4~5 倍。

## 二、改了什么

### 预览档输出 JPEG（`MemoryPreviewMWs.render`）

```ts
const useJpeg = meta.hasAlpha !== true;   // 只有带透明通道的才留 webp
await img.jpeg({
  quality: Config.Media.Photo.quality,   // 沿用全局 80
  mozjpeg: false,                        // libjpeg-turbo，比 mozjpeg 快一大截
  chromaSubsampling: '4:2:0',
  progressive: false,
  optimiseCoding: true,
});
```

- **带 alpha 的图仍出 webp** —— JPEG 没有透明通道，压平会变黑底。
- 缓存键从 `path` 改成 `path@size`（原来两个档位会撞车，现在虽然只用 2160，先修掉）。

### 诊断条改成报「服务端真实耗时 + 输出尺寸」

`<img>` 拉下来的资源，JS 拿不到响应头；但 `Server-Timing` 会被 Resource Timing
解析进 `entry.serverTiming`（同源可读），正好够用：

```
Server-Timing: pg2;dur=2485;desc="jpeg/gen/2160x2880/dct4"
```

诊断条（点画面 → `?vfdebug` 或设置里打开）里显示成：

```
服务端 JPEG · 现生成 · 2160×2880 · DCT理论1/4 · 2485ms
```

- `内存命中` / `现生成` 直接告诉你是不是在等服务端
- `DCT理论1/4` 只在够格的图（短边 ≥ 2×2160）上出现，标"理论"是因为上面已经证明它不生效
- 降级到 720 时显示 `fallback/720`

## 三、其他"快速办法"，逐个试过之后的结论

| 想法 | 实测 | 结论 |
|------|------|------|
| 换缩放核 lanczos3 → cubic / lanczos2 | 176→163 / 176→174（**只省 8%**） | 不动，画面一致性更重要 |
| 加 `sequentialRead` | 642 vs 641 ms | 无差别，不做 |
| 质量 80 → 78/85 | q85 体积 +18%，速度没差 | 不动 |
| 磁盘缓存预览档 | 第二遍 0 ms | 违背"不落盘"约定，等你点头再做 |
| 并发 2 → 3 | 巨图全解码是**单线程**，2 路已经吃满 2 核 | 会回到 1.3.16 的 CPU 打满，不做 |
| 预热并发 2 | 服务端给预热只留 1 个名额（给当前张让位） | 加了也没用 |
| 巨图降到 1440 档 | 全解码时间不变（2447ms 是地板），只省编码和传输 | 白掉画质，不做 |

**巨图的地板就是"全解码"**：8736×11648 这张，无论输出多大，都要 2.4s 解码。
想绕过它只能靠"提前做"（预热，1.3.18 已做）或"存起来别再做"（磁盘缓存）。
